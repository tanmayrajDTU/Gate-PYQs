01

Processes, Threads & System Calls

PROCESS STATES · PCB · CONTEXT SWITCH · THREADS VS PROCESSES

Process state diagram

Every process moves through a fixed set of states during its lifetime:

New → Ready → Running → (Waiting ⟷ Running) → Terminated Ready → Running: scheduler dispatch Running → Ready: timer interrupt / preemption Running → Waiting: I/O or event wait Waiting → Ready: I/O or event completion
The transition GATE tests most

A process can go directly from Running to Waiting (blocking for I/O) but NEVER directly from Waiting to Running — it must always pass through Ready first, to be re-selected by the scheduler.

Process Control Block (PCB) & context switch

The PCB stores everything needed to pause and later resume a process exactly where it left off: process state, program counter, CPU registers, memory-management info, scheduling info, and open file list (the exact field set is OS/architecture dependent). A context switch is the act of saving the current process's PCB and loading another's — it's scheduling/management overhead relative to the user workload, since no application instructions from either process execute during the switch itself (though the kernel bookkeeping it performs is still necessary work, not meaningless).

Process vs Thread

AspectProcessThread
Memory spaceOwn separate address spaceShares address space with sibling threads
Creation/switch costExpensive (heavyweight)Cheap (lightweight)
CommunicationNeeds IPC (pipes, shared memory, etc. — see Section 03's IPC breakdown below)Direct — shared memory already
Crash isolationOne process crashing doesn't affect othersOne thread crashing can bring down the whole process

System calls

The only sanctioned way for a user-mode process to request a kernel-mode service (file I/O, process creation, memory allocation). A system call triggers a mode switch — from user mode to kernel mode — and that transition itself carries overhead (saving/restoring context, privilege-level change), just like a context switch does. But don't conflate the two: unlike a context switch, the kernel-mode work a system call actually performs (reading the file, allocating the memory, creating the process) is useful, necessary computation — it's the mode-switch boundary that's overhead, not the system call as a whole.

GATE trap

fork() in Unix-like systems returns TWICE — once in the parent (with the child's PID) and once in the child (with return value 0). GATE frequently asks "how many processes are created" or "how many times is X printed" after a sequence of fork() calls — always trace both branches carefully; n fork() calls in sequence create 2ⁿ total processes.

Copy-on-write (COW) — how modern fork() avoids copying all of memory upfront

Naively, fork() sounds like it should duplicate the entire address space of the parent immediately — but that's expensive and often wasteful (many programs immediately call exec() after fork(), discarding the copy entirely). Modern Unix-style implementations instead use copy-on-write: right after fork(), the parent and child share the SAME physical pages, with both processes' page tables pointing to those pages and marked read-only (even for pages that were writable before the fork). No actual data is copied at fork() time.

The moment either process (parent or child) attempts to write to one of these shared pages, the read-only marking triggers a page fault. The kernel's fault handler recognizes this as a COW fault (not an illegal access), allocates a fresh physical page, copies the original page's content into it, updates the writing process's page table entry to point to the new page (now marked writable), and only then lets the write proceed. The other process's page table entry is untouched and still points to the original shared page.

This ties together three OS ideas in one mechanism: process creation (fork() itself), virtual memory (page tables mapping virtual pages to shared physical frames, with permission bits), and page faults (repurposed here not as "page missing from memory" but as "page present but access not yet permitted," triggering the actual copy). GATE can ask what happens on a write immediately after fork() — the answer involves a page fault even though the page was never absent from memory.

Practice — GATE style (original)

5 questions
Q1 A program calls fork() twice in sequence (not nested inside a conditional). Assuming both fork() calls succeed, how many total processes exist after both calls?

Each fork() doubles the number of processes executing the subsequent code. Starting from 1 process: after 1st fork → 2 processes; after 2nd fork (each of those 2 calls it) → 4 processes. (In reality fork() can fail — returning -1 with no child created — in which case fewer processes would exist; GATE questions of this style always intend the successful case unless stated otherwise.)

Answer: 4 processes (2² ), assuming both fork() calls succeed

Q2 Can a process move directly from the Waiting state to the Running state?

No — a waiting process must first move to Ready when its event/I/O completes, and only then can the scheduler dispatch it to Running.

Answer: No, it must pass through Ready first

Q3 What information is saved in a PCB during a context switch, and why is a context switch considered scheduling overhead?

A PCB typically saves process state, program counter, CPU register values, scheduling/accounting information, and references to memory-management information (e.g. page tables) and open files — the exact field list is OS/architecture dependent, not a fixed universal standard. It's overhead relative to the application workload because no user-process instructions from either process execute during the switch itself — the CPU is busy bookkeeping, not running application computation. That bookkeeping is still necessary kernel work, though, not meaningless work — "overhead" here means "not the workload," not "worthless."

Answer: State/PC/registers/memory-info/scheduling-info; it's overhead relative to user computation, since no application instructions run during the switch itself (the kernel bookkeeping is still necessary work)

Q4 Why is thread creation generally cheaper than process creation?

Threads within the same process share the address space, open files, and most other resources — creating a thread mainly needs a new stack and register set, whereas creating a process needs an entirely new address space and duplicated resources.

Answer: Threads share address space/resources, avoiding the duplication a new process requires

Q5 A system call is invoked. What mode transition occurs, and why is this necessary?

The CPU switches from user mode to kernel mode. This is necessary because privileged operations (direct hardware access, memory protection changes, etc.) must go through the kernel, which enforces the actual access checks — user code alone cannot be trusted to perform them safely.

Answer: User mode → kernel mode, to safely perform privileged operations

02

CPU Scheduling

FCFS · SJF · PRIORITY · ROUND ROBIN · TURNAROUND/WAITING TIME NUMERICALS

Key timing definitions — get these exactly right

Turnaround Time (TAT) = Completion Time − Arrival Time Waiting Time (WT) = Turnaround Time − Burst Time Response Time = Time of first CPU allocation − Arrival Time
The single most common numerical mistake

Waiting time is NOT completion time minus arrival time — that's turnaround time. Waiting time subtracts out the actual burst (execution) time too. Confusing these two is the #1 source of wrong answers in GATE scheduling numericals.

Scheduling algorithms — comparison

AlgorithmPreemptive?Selection criterionKey drawback
FCFS (First-Come-First-Served)NoArrival orderConvoy effect (short jobs stuck behind long ones)
SJF (Shortest Job First)NoSmallest burst timeStarvation of long jobs; needs burst time known in advance
SRTF (Shortest Remaining Time First)YesSmallest remaining burst timeSame starvation risk, plus frequent context switches
Priority SchedulingEitherHighest priorityStarvation of low-priority processes (aging can reduce/prevent this — see note below)
Round RobinYesFixed time quantum, cyclic orderToo-small quantum ⟹ excessive context-switch overhead
Provably optimal (average waiting time) — with assumptions

Non-preemptive SJF minimizes average waiting time — but only under the standard scheduling-theory assumptions GATE questions implicitly rely on: (1) it's the non-preemptive variant being compared (SRTF is the preemptive analogue and optimal in its own preemptive class); (2) burst times are known in advance exactly — real schedulers only estimate them; (3) the objective is specifically minimizing average waiting time — SJF is not optimal for other objectives like maximum waiting time or fairness; (4) the comparison is over the full, fixed set of jobs considered together (all present/arriving as modeled), under the standard single-CPU scheduling model. Drop any of these and the optimality claim can break.

Aging — a mitigation, not a magic fix

Don't state it as "aging fixes starvation" — the more accurate claim is: aging can prevent or reduce indefinite starvation by gradually increasing the priority of processes the longer they wait, so a long-waiting low-priority process eventually becomes high-priority enough to run. It doesn't guarantee every possible starvation scenario is eliminated — the exact behaviour depends on the aging rate, how quickly new high-priority work keeps arriving, and the specific scheduling policy layered on top of it. Treat aging as a well-known mitigation technique, not an absolute guarantee.

Worked example — FCFS

Process Arrival Burst P1 0 5 P2 1 3 P3 2 8 FCFS order: P1, P2, P3 (by arrival) P1: starts 0, ends 5 → TAT=5, WT=0 P2: starts 5, ends 8 → TAT=7, WT=4 P3: starts 8, ends 16 → TAT=14, WT=6 Average WT = (0+4+6)/3 = 3.33
GATE trap

Round Robin's average waiting time is highly sensitive to the time quantum — too large approaches FCFS behavior (and its convoy effect), too small causes excessive context-switch overhead. GATE often asks for the "ideal" quantum reasoning: a good quantum is slightly larger than the average burst time, not the smallest possible value.

Practice — GATE style (original)

5 questions
Q1 P1(AT=0,BT=6), P2(AT=1,BT=4), P3(AT=2,BT=2). Using non-preemptive SJF, find the execution order.

At t=0, only P1 has arrived, so it must start (SJF is non-preemptive, so once started it runs to completion). At t=6, P2(BT4) and P3(BT2) have both arrived — pick smaller: P3, then P2.

Answer: P1 → P3 → P2

Q2 For P1(AT=0,BT=4), P2(AT=0,BT=3) under FCFS (P1 first), find the waiting time of P2.

P1 runs 0→4 (WT=0). P2 starts at 4, completes at 4+3=7. TAT of P2 = 7−0=7. WT = TAT − BT = 7−3.

Answer: WT(P2) = 4

Q3 Two processes P1(BT=10) and P2(BT=2) both arrive at t=0. Round Robin with quantum=4. Trace the schedule and find P2's waiting time.

t=0-4: P1 runs first (ready queue order: P1, P2), consuming its full quantum with 6 units remaining. t=4-6: P2 finally gets to run and completes (BT=2, finishes at t=6). P2 arrived at t=0 but had to wait while P1 occupied the CPU for its first quantum — so P2 sits idle in the ready queue from t=0 to t=4 (4 units of waiting) before starting its only run at t=4.

Answer: WT(P2) = 4 (P2 waits from t=0 to t=4, then runs to completion with no further waiting)

Q4 Why does SJF risk starvation, and what does Round Robin guarantee that SJF does not?

SJF always favors shorter jobs, so a long job can be perpetually pushed back if shorter jobs keep arriving — no upper bound on its wait. Round Robin, by cycling through all ready processes with a fixed quantum, provides fairness: under the standard model of a finite, fixed ready set, every continuously-ready process gets CPU time within a bounded number of turns — roughly one cycle through the ready queue. With processes continuously arriving and leaving, the exact wait bound depends on how many processes are competing at any given time, so "guaranteed within one cycle" isn't a universal law — the key guaranteed property is that no ready process is skipped indefinitely (no starvation), unlike SJF.

Answer: SJF can starve long jobs indefinitely; RR guarantees no process is skipped indefinitely — bounded wait (roughly one cycle under a fixed ready set, more generally bounded by the number of competing processes)

Q5 P1(AT=0,BT=8) and P2(AT=1,BT=4) with SRTF (preemptive). At what time (if any) does preemption occur, and why?

At t=1, P1 has 7 units remaining while newly-arrived P2 needs only 4. Since SRTF always picks the smallest REMAINING time, P2 preempts P1 at t=1.

Answer: Preemption occurs at t=1 (P2's remaining time 4 < P1's remaining time 7)

03

Synchronization & IPC

CRITICAL SECTION · SEMAPHORES · MUTEX · CLASSIC SYNC PROBLEMS · IPC (SHARED MEMORY, MESSAGE PASSING, PIPES, SIGNALS)

Critical section requirements

RequirementMeaning
Mutual ExclusionAt most one process in the critical section at a time
ProgressIf no process is in the CS, a waiting process must eventually be allowed to enter (no indefinite postponement by non-waiting processes)
Bounded WaitingA limit exists on how many times other processes can enter before a waiting process gets its turn

Peterson's algorithm — a software-only solution for 2 processes

Peterson's algorithm solves mutual exclusion for exactly two processes (P0 and P1) using only two shared variables — no hardware support required. It's the classic textbook proof that mutual exclusion is achievable in software alone.

shared: boolean flag[2] = {false, false}; // flag[i]: does Pi want to enter? shared: int turn; // whose turn is it if both want in? Process Pi (the other process is Pj, j = 1−i): flag[i] = true; // I want to enter turn = j; // but be polite — let the other go first if it also wants in while (flag[j] && turn == j) ; // busy-wait <critical section> flag[i] = false; // done, I no longer want in
Why all three properties hold

Mutual exclusion: both processes in the CS simultaneously would require turn to equal both 0 and 1 at once — impossible, since turn is a single variable set last by whichever process entered second (its "turn = j" write is the more recent one, so the other process's wait condition holds). Progress: if only one process wants in, its own flag check on the other's (false) flag[j] lets it proceed immediately; if both want in, exactly one value of turn can hold at a time, so exactly one process's wait condition is false and it proceeds. Bounded waiting: after a process exits the CS (setting its flag to false), the other process — if waiting — enters next, and can be made to wait for at most one entry by the first process before its own turn, so no indefinite postponement occurs.

This is a busy-waiting (spinlock-style) solution — the while loop spins consuming CPU cycles rather than blocking, exactly like the spinlock implementation of semaphore wait() discussed below.

Hardware synchronization primitives

Peterson's algorithm shows mutual exclusion is possible in pure software, but real systems mostly rely on atomic hardware instructions instead — a single CPU instruction that reads and modifies a memory location as one indivisible (uninterruptible) step, which sidesteps the need for the kind of careful multi-variable protocol Peterson's algorithm requires.

PrimitiveEffect (atomic)
Test-and-Set (TAS)Reads the old value of a boolean/lock variable, unconditionally sets it to true, and returns the old value — all as one indivisible step
Compare-and-Swap (CAS)Compares a memory location's current value to an expected value; if they match, swaps in a new value (all atomically) and reports success — the basis of modern lock-free data structures
Swap / XCHGAtomically exchanges the values held in two memory locations (or a register and a memory location)
Building a lock from Test-and-Set
lock (shared boolean, init false): acquire(): while (TestAndSet(lock) == true) ; // busy-wait — someone else holds it release(): lock = false;

Because TestAndSet is atomic, only one process can ever see the lock flip from false to true (get "old value = false") at a given moment — that process is the one that acquires the lock; every other concurrent caller sees "old value = true" and keeps spinning. This is also busy-waiting, same as Peterson's algorithm and the spinlock version of semaphore wait().

The synchronization hierarchy, from lowest level to highest

Peterson's algorithm — a pure software solution, works only for 2 processes, needs no special hardware. Test-and-Set / Compare-and-Swap / Swap — atomic hardware instructions that any number of processes can use as a building block; still busy-waiting on their own. Semaphore / Mutex — higher-level synchronization abstractions, typically implemented on top of one of these hardware primitives, that add blocking (rather than pure spinning) and richer semantics (counting, ownership). GATE questions that ask "what's the lowest-level mechanism here" usually want the hardware primitive, not the semaphore built on top of it.

Semaphores

wait(S) [a.k.a P(S)]: decrement S; if S < 0 (no resource available), block the calling process signal(S) [a.k.a V(S)]: increment S; if a process was blocked on S, wake one of them Binary semaphore: S ∈ {0,1} — behaves like a mutex lock Counting semaphore: S can take any integer — controls access to a pool of k resources (init S=k)
This is the semantic definition, not one implementation

wait/signal are defined by their effect (block when unavailable, wake a waiter on release) — how that's implemented is a separate design choice. A textbook spinlock implementation of wait(S) is while(S ≤ 0); S = S − 1;, which busy-waits instead of blocking. That's one valid implementation, not the definition of a semaphore.

Mutex vs Binary Semaphore — the subtle distinction

They look identical in code, but conceptually a mutex is meant to be released only by the process that acquired it (ownership matters). A binary semaphore has no ownership concept — any process can signal it, even one that never called wait. GATE occasionally tests this conceptual distinction directly.

Priority inversion

A classic trap that combines priority scheduling with locking: a high-priority process needs a lock currently held by a low-priority process, so it must wait. Meanwhile, an unrelated medium-priority process keeps preempting the low-priority process (since it doesn't need the lock and simply outranks it) — so the low-priority process rarely gets to run, finish its critical section, and release the lock. Net effect: the high-priority process is effectively blocked by the medium-priority one, inverting the intended priority order.

Two standard mitigations: priority inheritance — the low-priority process temporarily inherits the waiting high-priority process's priority while it holds the lock, so medium-priority processes can no longer preempt it; and priority ceiling — the lock itself is assigned a priority ceiling (the highest priority of any process that might lock it), and any process holding it runs at that ceiling priority immediately, preventing the inversion from arising at all.

Classic synchronization problems — the recognizable signature

ProblemCore constraint
Producer-Consumer (bounded buffer)Producer waits if buffer full; consumer waits if buffer empty
Readers-WritersMultiple readers can read simultaneously; writers need exclusive access
Dining PhilosophersShared resources (forks) arranged in a cycle — classic deadlock-risk scenario
GATE trap

The busy-waiting implementation of wait(S) — while(S ≤ 0); S = S − 1; — wastes CPU cycles spinning instead of blocking. GATE sometimes calls this a "spinlock" and contrasts it with the blocking implementation (which puts the waiting process on a queue instead of spinning). Know both exist and which one is implied by the question's context.

Practice — GATE style (original)

7 questions
Q1 A counting semaphore is initialized to 3. After 2 wait() calls and 1 signal() call, what is its value?

Start=3. wait() decrements: 3→2→1 (after 2 waits). signal() increments: 1→2 (after 1 signal).

Answer: 2

Q2 Which critical-section requirement is violated if a process waiting to enter can be bypassed by other processes an unbounded number of times?

This directly violates Bounded Waiting — there must be a finite limit on how many times others can enter before the waiting process gets a turn.

Answer: Bounded waiting

Q3 In the Producer-Consumer problem with a bounded buffer of size 5, if 3 items are currently in the buffer, and the "empty" counting semaphore starts at 5, what is its current value?

The "empty" semaphore tracks empty slots — it decreases by 1 each time an item is produced (wait) and increases when consumed (signal). Starting at 5 with 3 items produced (and none consumed yet, matching "3 items currently in buffer"): 5−3.

Answer: empty = 2 (2 slots remain empty)

Q4 Why can a binary semaphore substitute for a mutex in most code, but the reverse substitution is conceptually risky?

A binary semaphore has no notion of ownership — any thread can call signal() on it even without having called wait(), which can accidentally "unlock" a resource that thread never locked. A true mutex enforces that only the owner can release it, which is a safety property binary semaphores don't guarantee by construction.

Answer: Binary semaphores lack ownership enforcement that a mutex guarantees

Q5 In the Readers-Writers problem, can two readers access the shared resource simultaneously? Can a reader and a writer?

Yes — multiple readers can read concurrently since reading doesn't modify data. No — a writer requires exclusive access, so no reader (or other writer) can access the resource while a writer is active.

Answer: Readers can share access; writers require full exclusivity

Q6 In Peterson's algorithm, why does the mutual exclusion argument fail if the shared turn variable is removed and only flag[] is kept?

Without turn, both processes could set their own flag to true and then both find the other's flag also true at essentially the same moment, with no tiebreaker variable to decide who waits and who proceeds — both could then busy-wait on each other forever (violating progress) or, depending on the exact race, both could see the other's flag flip false-to-true-to-false and slip into the critical section together (violating mutual exclusion). The turn variable exists precisely to break this symmetry deterministically.

Answer: Without turn there's no tiebreaker when both processes want in simultaneously — the algorithm can no longer guarantee mutual exclusion or progress

Q7 Why is Test-and-Set preferred over Peterson's algorithm for building a lock usable by more than 2 processes?

Peterson's algorithm is specifically designed for exactly 2 processes — its correctness argument relies on a single shared turn variable that only makes sense between two parties (extending it to n processes needs a fundamentally different, more complex protocol, e.g. the bakery algorithm). Test-and-Set, by contrast, is a single atomic hardware instruction that works identically no matter how many processes are contending for the lock — any number of processes can spin on the same TestAndSet call, and atomicity guarantees exactly one succeeds at a time.

Answer: Peterson's algorithm doesn't generalize past 2 processes without a different protocol; Test-and-Set works for any number of processes as-is

Synchronization vs communication — the distinction GATE expects

Two different problems, often mixed up

Synchronization (semaphores, mutexes, monitors) controls the ordering/timing of access to shared resources — it doesn't by itself move data between processes. Inter-process communication (IPC) is about actually exchanging data between processes, which may or may not need synchronization alongside it (e.g. shared memory needs synchronization to be safe; a well-designed message queue often handles ordering internally). Threads communicate "for free" via shared address space and mainly need synchronization; processes need explicit IPC mechanisms since they don't share memory by default.

Inter-process communication (IPC) mechanisms

Since processes (unlike threads) have separate address spaces, they need OS-provided channels to exchange data. The two broad models are shared memory and message passing; everything else below is a specific mechanism implementing one of those models.

ModelHow data movesTrade-off
Shared memoryOS maps a region of physical memory into both processes' address spaces; they read/write it directly, no kernel involvement per accessFast (no per-message syscall overhead) but requires explicit synchronization by the processes (e.g. semaphores) to avoid races
Message passingProcesses exchange discrete messages via send()/receive(), routed through the kernelSimpler to get correct (no shared-state races), naturally handles synchronization, but slower — every message is a kernel-mediated copy

Pipes

A unidirectional byte-stream channel, typically between a parent and child process (created before fork(), then inherited). Data written at one end is read in FIFO order at the other. Exists only in kernel memory for the lifetime of the processes holding it open — no filesystem name.

Named pipes (FIFOs)

Functionally the same byte-stream idea as a pipe, but given a name in the filesystem (a FIFO special file), so unrelated processes (not just parent/child) can open it by name and communicate — this is the key difference from a plain pipe.

Signals

A lightweight, asynchronous notification mechanism — the OS delivers a small integer signal (e.g. SIGKILL, SIGTERM, SIGCHLD) to a process, interrupting its normal flow to run a signal handler (or a default action like terminate). Carries almost no data (just which signal fired) — it's a notification/control mechanism, not a channel for transferring payloads like pipes or shared memory are.

Sockets — supporting

A message-passing endpoint that works both locally (same machine, via Unix domain sockets) and across a network (via TCP/IP sockets) — the same API extends IPC beyond a single machine. Lower GATE priority than pipes/shared memory/signals, but useful to recognize as the mechanism that generalizes message passing to distributed systems.

One-line IPC comparison to memorize

Shared memory = fast, needs your own synchronization. Message passing (pipes, named pipes, sockets) = slower, kernel-mediated with synchronization semantics provided by the communication primitives themselves (e.g. blocking reads/writes). Signals = not really "data transfer," just async notification.

Practice — IPC (original)

4 questions
Q1 Two unrelated processes (no parent-child relationship) need to communicate via a byte stream. Can a plain (unnamed) pipe be used? What should be used instead?

Normally no — a plain pipe only exists as an inherited file descriptor, so it's typically shared only between a process and its descendants (who received the descriptor via fork()). Unrelated processes generally need a named pipe (FIFO), which has a filesystem path either process can open independently — or another IPC mechanism. (Note: an unrelated process could still gain access to an unnamed pipe's descriptor if it were explicitly passed to it, e.g. via a Unix domain socket using SCM_RIGHTS — the "only descendants" rule is the normal case, not an absolute limitation of pipes themselves.)

Answer: Not by default; use a named pipe (FIFO) or another IPC mechanism instead

Q2 Why does shared memory IPC need explicit synchronization but message passing typically doesn't need the processes to add their own?

Shared memory requires explicit synchronization because multiple processes directly access the same memory and can race. Message-passing systems provide synchronization semantics through operations such as send/receive, but the exact ordering and blocking guarantees depend on the IPC mechanism — whether it is blocking or non-blocking, synchronous or asynchronous, buffered or unbuffered. So message passing doesn't universally eliminate ordering concerns; it just supplies ordering through its communication primitives rather than requiring the processes to bolt on their own.

Answer: Shared memory requires explicit synchronization; message passing provides synchronization through its communication primitives, with exact ordering depending on the mechanism.

Q3 A process receives SIGCHLD. What does this signal typically indicate, and does it carry the child's exit data directly?

SIGCHLD typically indicates a child process has terminated or stopped. As a notification, it should not be treated as the mechanism for reaping the child — the parent normally calls wait()/waitpid() to obtain and reap the child's exit status. (On POSIX systems using the SA_SIGINFO handler flag, the signal's siginfo_t can carry some information such as the child's PID and status, but wait()/waitpid() is still what actually reaps the child and retrieves the full wait status.)

Answer: Notifies that a child changed state; exit data must be separately fetched via wait()

Q4 Why are Unix domain sockets and TCP sockets both classified under "message passing" rather than "shared memory" IPC?

Both move discrete messages/byte streams through kernel-mediated send/receive (or read/write) calls rather than exposing a shared region of memory both processes access directly — the defining feature of the message-passing model, regardless of whether the peer is local or remote.

Answer: Both use kernel-mediated send/receive rather than a directly shared memory region

Deadlock

4 NECESSARY CONDITIONS · RESOURCE ALLOCATION GRAPH · BANKER'S ALGORITHM

The four necessary conditions (Coffman conditions)

All four must hold simultaneously for a deadlock to occur — breaking any single one prevents deadlock:

ConditionMeaning
Mutual ExclusionAt least one resource must be held in a non-shareable mode
Hold and WaitA process holding a resource is waiting to acquire more
No PreemptionResources can't be forcibly taken away — only voluntarily released
Circular WaitA cycle of processes exists, each waiting for a resource held by the next

Resource Allocation Graph (RAG) — the fast visual check

Cycle detection rule

With single-instance resources: a cycle in the RAG ⟺ deadlock exists. With multiple-instance resources: a cycle is necessary but NOT sufficient for deadlock — you must additionally verify no valid execution order exists that resolves it.

Banker's Algorithm — safety check

Determines whether a system state is "safe" (some order exists in which all processes can complete) before granting a resource request. A state is safe if a sequence of processes exists such that each process's remaining need can be satisfied by currently available resources plus resources released by already-finished processes in the sequence.

Need[i] = Max[i] − Allocation[i] A request from process i is granted only if it can be satisfied AND the resulting state remains safe
GATE trap

An "unsafe" state is NOT automatically a deadlocked state — it simply means the system cannot GUARANTEE avoiding deadlock; deadlock might still not actually occur depending on future requests. Don't conflate "unsafe" with "deadlocked" — Banker's algorithm is deliberately conservative.

Deadlock vs Starvation — don't conflate the two

DeadlockStarvation
What happens to processesWait indefinitely due to a cyclic resource dependencyA process may repeatedly lose access to the CPU/resource, without any cycle involved
Progress of the systemThe specific set of mutually-blocked processes makes zero progress — they're permanently stuckOther processes continue making progress just fine; only the unlucky (typically low-priority) process is denied service
Typical fixBreak one of the four Coffman conditions (prevention), or run detection/avoidance (Banker's algorithm)Aging, or a fair scheduling policy (e.g. Round Robin) that guarantees every process eventually gets a turn
The core distinction, in one line

Deadlock is a mutual, cyclic block — a specific group of processes is stuck waiting on each other, and no external event resolves it without intervention. Starvation is a one-sided, ongoing disadvantage — one process (or a few) keeps losing out to others under a scheduling/allocation policy that's individually reasonable each time, but collectively unfair over the long run; the system as a whole keeps making progress, just never for that unlucky process. A deadlocked process is, in a sense, always starving (it's waiting forever) — but a starving process is not necessarily deadlocked (the resource it wants is repeatedly available, it's just repeatedly given to someone else first).

Practice — GATE style (original)

5 questions
Q1 If all resources involved in the system can be safely preempted from a process without harm, can deadlock occur?

No — if every resource that could be part of a hold-and-wait cycle can be preempted, the "No Preemption" necessary condition is broken for the whole system, and deadlock cannot occur regardless of the other three conditions. (Note: if only *some* resources are preemptable while others involved in a potential cycle are not, deadlock can still occur via the non-preemptable resources — the guarantee only holds when preemption is possible for all relevant resources.)

Answer: No, deadlock cannot occur (No Preemption condition is violated for all resources)

Q2 A RAG with single-instance resources has no cycle. Is deadlock possible right now?

For single-instance resource systems, a cycle in the RAG is both necessary and sufficient for deadlock. No cycle means deadlock is not currently present.

Answer: No deadlock currently exists

Q3 Total instances of resource R = 10. Currently allocated: P1=3, P2=4, P3=2. Available = ?

Available = Total − sum of allocations = 10 − (3+4+2) = 10 − 9.

Answer: Available = 1

Q4 Process P has Max=[7,5,3], Allocation=[2,1,1]. Find Need.

Need = Max − Allocation = [7−2, 5−1, 3−1].

Answer: Need = [5, 4, 2]

Q5 A system is found to be in an "unsafe" state by Banker's algorithm. Does this guarantee deadlock will occur?

No — "unsafe" means the algorithm cannot guarantee a completion sequence exists for all currently claimed future requests; it does not mean deadlock is certain. Processes might still request resources in an order that avoids deadlock, but the system can no longer promise this.

Answer: No — unsafe ≠ deadlocked; it only means safety can no longer be guaranteed

Memory Management

PAGING · SEGMENTATION · PAGE TABLES · ADDRESS TRANSLATION · DEMAND PAGING · PAGE FAULTS · VIRTUAL MEMORY · PAGE REPLACEMENT · TLB

Paging — fixed-size division

Logical address = (Page number, Offset) Physical address = (Frame number, Offset) [offset is identical in both — only the page→frame mapping changes] Number of bits for page number = log₂(number of pages) Number of bits for offset = log₂(page size)
Why paging eliminates external fragmentation

Since pages and frames are fixed, equal-sized units, any free frame can hold any page — there's no need for contiguous physical memory. Internal fragmentation can still occur though (last page of a process may not fully use its frame).

Segmentation — variable-size, logical division

Divides memory by logical units (code segment, stack segment, heap segment) rather than fixed size. Suffers from external fragmentation (variable-sized holes) but maps more naturally onto how programs are actually structured.

Contiguous allocation strategies — finding a hole for a new process

Before a process can run in a contiguous (non-paged) memory model, the OS must pick WHICH free hole to give it when several are large enough. Four classic strategies:

StrategyBasic idea
First FitFirst sufficiently large hole
Best FitSmallest sufficiently large hole
Worst FitLargest hole
Next FitContinue search from previous position
GATE trap — Best Fit is not actually "best" in practice

Despite the name, Best Fit is NOT generally the best-performing strategy — choosing the tightest possible hole leaves behind slivers of memory too small to be useful for future allocations, causing rapid external fragmentation. Empirically, First Fit and Best Fit tend to perform similarly and generally better than Worst Fit in both speed and memory utilization — don't assume Best Fit wins on both fragmentation and speed just because of its name. Next Fit avoids First Fit's tendency to leave many small fragments clustered near the start of memory, by resuming the scan from where it last stopped rather than always restarting from address 0.

Virtual vs physical address, and the page table

A process only ever sees virtual (logical) addresses — the address space it believes it owns, starting at 0. The MMU (memory management unit) translates each virtual address to a physical address — the actual location in RAM — using the process's page table, which the OS maintains per-process. Virtual memory decouples "how much address space a program can use" from "how much physical RAM actually exists," letting the OS run processes whose total virtual footprint exceeds physical memory.

Address translation (single-level): 1. Split virtual address into (page number, offset) 2. Look up page number in the page table → get frame number (+ valid/invalid bit, protection bits) 3. Physical address = (frame number, offset) [offset unchanged — only the page→frame part translates]
Why a single-level page table doesn't scale

A page table needs one entry per page in the virtual address space — for a 32-bit address space with 4KB pages, that's 2²⁰ (~1 million) entries, and every process needs its own table. Multi-level (hierarchical) paging fixes this: the virtual address is split into multiple page-number fields (outer, inner, offset), each indexing into a smaller table, and outer-level entries for unused regions of the address space are simply left invalid — so sparsely-used address spaces don't need every leaf table allocated.

Multi-level (2-level) translation: Virtual address = (outer page #, inner page #, offset) 1. Outer page # indexes the outer (root) page table → gives address of an inner page table 2. Inner page # indexes that inner page table → gives frame number 3. Physical address = (frame number, offset) Cost: 2 memory accesses just for translation (before the actual data access) if the TLB misses — this compounds with more levels.
Page-table memory overhead — the numerical GATE actually asks

Single-level page table size = (number of pages) × (bytes per page-table entry). This can itself be enormous for large address spaces with small pages — which is precisely the motivation for multi-level tables (only allocate the inner tables that are actually needed) and for the TLB (avoid repeatedly paying the page-table lookup cost at all).

Page faults & demand paging

A page fault is the trap that occurs when a process accesses a page whose valid bit is 0 in the page table — but a valid bit of 0 itself covers two different situations, and the OS has to tell them apart when handling the trap. If the reference is to a legitimate part of the process's address space that simply isn't currently resident (e.g. it's been paged out, or never yet loaded under demand paging), the OS obtains/constructs the needed page — commonly by loading it from disk (secondary storage) into a free frame, though depending on the case it could also be a zero-filled page, a copy-on-write copy, or another backing mechanism — updates the page table, and resumes the instruction — this is the common "page not resident" case. But if the reference is to an address the process has no business touching at all (outside its allocated address space, or violating protection bits), there's no page to fetch from disk — the OS instead treats it as an illegal/invalid memory reference, typically delivering a segmentation-fault-style signal that can terminate the process. Both cases start as the same trap (valid bit = 0), but they diverge sharply in how the OS resolves them. Demand paging is the strategy of loading legitimately-resident-but-not-yet-loaded pages into memory only when first referenced (lazily), rather than loading a process's entire address space upfront — it's what makes virtual memory practical, since most programs never touch every page they could.

GATE trap — page fault vs TLB miss, don't conflate them

A TLB miss just means the translation isn't cached — the page table (in memory) is still consulted and usually succeeds, costing one extra memory access. A page fault means the page genuinely isn't in physical memory at all — it requires a disk access (orders of magnitude slower) and possibly evicting another page. Every page fault implies the TLB also missed, but a TLB miss does NOT imply a page fault.

Effective Access Time with page faults

EAT (with page-fault probability p) = (1−p)·(memory access time) + p·(page fault service time) Page fault service time typically includes: trap overhead + disk I/O time to fetch the page + restart overhead — this is on the order of milliseconds, vs nanoseconds for a normal memory access, so even a small p dominates EAT.

This is a distinct numerical setup from the TLB-hit-ratio EAT formula above — TLB EAT compares "cached translation" vs "page-table lookup," while page-fault EAT compares "page present in memory" vs "page fetched from disk." GATE sometimes combines both into one multi-level EAT problem (TLB hit/miss, then page present/fault) — read carefully which probabilities are given for which stage.

3 questions
Q1 A 32-bit virtual address space uses 4KB pages and a single-level page table with 4-byte entries. How large is the page table for one process?

Number of pages = 2³² / 2¹² = 2²⁰. Page table size = 2²⁰ entries × 4 bytes = 2²² bytes = 4MB per process — this is exactly the overhead that motivates multi-level paging.

Q2 A process accesses a page with valid bit = 0, and the reference is to a legitimate (in-bounds) part of the address space that simply isn't resident right now. What happens, and how is this different from a TLB miss on a page with valid bit = 1?

Valid bit = 0 triggers a page fault. Here, since the reference itself is legitimate, the OS traps, obtains/constructs the needed page — commonly by reading it from disk (swap or a file-backed mapping), but it could also be a zero-filled page, a copy-on-write copy, or another backing mechanism depending on the system — updates the page table, and restarts the instruction. When disk I/O is involved this is a disk-speed operation, though not every legitimate page fault requires it. (If the access had instead been to an out-of-bounds or protection-violating address, the same valid-bit-0 trap fires, but the OS has nothing to fetch or construct — it instead treats it as an illegal reference, which can terminate the process, e.g. a segmentation fault.) A TLB miss on a page with valid bit = 1 is a much cheaper case: it just means the cached translation wasn't found; the page table (already in memory) is consulted directly — a memory-speed operation, no disk I/O.

Answer: Page fault on a legitimate but non-resident page → OS handles the fault and obtains/constructs the page (commonly via disk I/O, but not always); the same trap on an illegal reference instead raises an access violation; TLB miss on a resident valid page = one extra memory access only

Q3 Memory access = 100ns, page fault service time = 8ms, page fault rate p = 0.001. Assume the given page-fault service time already covers the full fault handling (trap + disk I/O + restart) and does NOT separately include the eventual memory access that follows the fault — so that access isn't double-counted. Find the EAT.

EAT = (1−p)(memory time) + p(page fault service time) = 0.999(100ns) + 0.001(8,000,000ns) = 99.9ns + 8000ns ≈ 8099.9ns. (If a question instead states that the page-fault service time excludes the final memory access, you'd add one more p×(memory time) term — the numerical difference here is negligible since 100ns is tiny next to 8ms, but for smaller service times relative to access time it matters, so always check which model the question intends.)

Answer: EAT ≈ 8100 ns (≈8.1 µs) — note how even p=0.001 makes the fault term dominate completely

Translation Lookaside Buffer (TLB)

Effective Access Time (EAT) = h·(TLB time + Memory time) + (1−h)·(TLB time + 2×Memory time) where h = TLB hit ratio

A TLB hit needs one memory access (data); a TLB miss needs two (page table, then data) — this is the standard EAT numerical setup GATE uses repeatedly.

Consolidated EAT formula sheet — don't mix these two scales
CaseWhat happensCost (order of magnitude)
TLB hitTLB lookup + one memory access (for the data itself)Nanoseconds — TLB time + Memory time
TLB miss (page still in memory)TLB lookup + page-table access (in memory) + memory access (for the data)Nanoseconds — TLB time + 2×Memory time (page table lookup counted as one memory access)
Page fault (page NOT in memory)Trap + disk I/O to fetch the page + restart, on top of whatever TLB/page-table work already happenedMilliseconds — orders of magnitude larger than either TLB case

Keep these as two separate EAT computations layered on top of each other, not one formula: first resolve TLB hit/miss (nanosecond scale, using h) to get the address translation, THEN separately account for whether the resulting page is actually resident or needs to page-fault in (millisecond scale, using p). A combined problem gives you both h and p and expects: EAT = (TLB-level EAT) blended with the page-fault term — e.g. EAT ≈ [TLB/page-table cost] + (1−p)(memory time) + p(page fault service time). Because the page-fault term is so much larger, even a small p will dominate the total far more than the TLB hit ratio does — don't let the TLB formula distract from that.

Page replacement algorithms

AlgorithmRuleNotable behavior
FIFOEvict the oldest-loaded pageCan suffer Belady's Anomaly (more frames → more faults, counter-intuitively)
Optimal (OPT/MIN)Replaces the page whose next use is farthest in the futureTheoretical best case — not implementable online, since future references are unknown
LRUEvict the least-recently-used pageGood practical approximation of OPT/MIN; never suffers Belady's Anomaly
One canonical name — Optimal (OPT/MIN)

This algorithm goes by three names in textbooks and question papers — Optimal, OPT, and MIN — all referring to the exact same rule: replace the page whose next use is farthest in the future (equivalently, the page that won't be needed for the longest time, or that may never be needed again). It is theoretically optimal — provably minimizes page faults for a given reference string and frame count — but is generally not implementable online, because it requires knowing the future reference string in advance. It's used only as a theoretical benchmark to evaluate how close a practical algorithm (like LRU) comes to the best possible.

GATE trap — the general theory behind Belady's Anomaly

Belady's Anomaly (more page frames causing MORE page faults) is a signature property specifically of FIFO — it does NOT occur with LRU or Optimal (OPT/MIN) replacement. GATE frequently asks you to trace a reference string under FIFO with two different frame counts specifically to demonstrate this anomaly.

The deeper, more testable reason: a replacement algorithm is called a stack algorithm if, for any reference string, the set of pages resident with k frames is always a subset of the set resident with k+1 frames, at every point in time. This subset property mathematically guarantees page faults can only stay the same or decrease as frames increase — never increase — so stack algorithms never suffer Belady's Anomaly, by construction (it's not just an empirical observation). LRU and Optimal (OPT/MIN) are both stack algorithms — LRU because the k most-recently-used pages are always a subset of the k+1 most-recently-used pages; Optimal because the k pages needed soonest are always a subset of the k+1 pages needed soonest. FIFO is NOT a stack algorithm — the "oldest loaded" page depends on load order, not recency of use, so no such subset relationship holds in general, which is exactly why it's vulnerable to the anomaly.

Thrashing and the working-set model

The classic causal chain: too many processes running concurrently → each gets too few frames → excessive page faults per process → the CPU spends most of its time servicing page faults (paging) instead of executing → CPU utilization collapses → thrashing. Counter-intuitively, the OS's usual fix for low CPU utilization (admit more processes, i.e. increase the degree of multiprogramming) is exactly what CAUSES thrashing in the first place — it shrinks each process's frame allocation further, triggering even more faults, in a vicious cycle.

Working set

The working set of a process at a given time is the set of pages it has actively referenced during a recent window of Δ references (the working-set window) — an approximation of the pages that process actually needs resident in memory right now to run without excessive faulting.

Working-set model as thrashing prevention

If the sum of all processes' working-set sizes exceeds the total number of available frames, thrashing can occur — there simply isn't enough physical memory to hold what everyone actively needs at once. The OS can use this as an admission-control rule: only start a new process (or bring a suspended one back in) if doing so wouldn't push total working-set demand over the available frame count — trading a lower degree of multiprogramming for actually-productive CPU time, instead of chasing utilization by over-committing frames.

Q4 Same reference string and frame count as Q3, but why might using LRU instead never exhibit Belady's Anomaly if frames were increased to 4?

LRU is a "stack algorithm" — the set of pages held with k frames is always a subset of what would be held with k+1 frames at every step. This subset property mathematically guarantees that page faults can only decrease (or stay the same), never increase, as frames increase — unlike FIFO.

Answer: LRU has the stack property, which structurally prevents Belady's Anomaly

Q5 Why does segmentation suffer from external fragmentation while pure paging does not?

Segments are variable-sized, so as segments are allocated and freed over time, memory becomes divided into non-contiguous free blocks that may be too small individually to satisfy a new request even though total free memory is sufficient. Paging avoids this since all frames are the same fixed size — any free frame fits any page.

Answer: Variable segment sizes create unusable gaps; paging's fixed-size frames don't

File Systems & I/O

File metadata & the inode concept

A file is more than its data bytes — the OS tracks metadata separately: owner, permissions, size, timestamps (created/modified/accessed), and the list of blocks holding the data. In Unix-style systems this metadata lives in an inode (index node) — a fixed-size structure holding all of it except the filename, plus pointers to the data blocks (often via indexed allocation, sometimes with direct pointers for small files and indirect pointers for large ones). The filename itself lives only in the directory entry, which just maps name → inode number — this is why hard links work: multiple directory entries can point to the same inode.

Directory structures

The OS needs to track which blocks are unallocated so it knows where new files/extensions can go. Two standard schemes:

Protection & permissions

Access control is typically expressed per file as a set of permissions (read/write/execute) for distinct classes of user — commonly owner, group, and others in Unix-style systems (the familiar rwx rwx rwx triad). More fine-grained systems use access control lists (ACLs), listing specific permissions per individual user/group rather than just three fixed classes. GATE mainly expects you to recognize the owner/group/other model and reason about what a given permission bit pattern allows.

File allocation methods — and the underlying trade-off

Allocation is fundamentally a trade-off between sequential access efficiency + simplicity (contiguous) and flexible growth + random access (linked/indexed) — no single method wins on every axis, which is why GATE questions usually ask you to pick the right one for a stated access pattern rather than name "the best" method in the abstract.

MethodHow it worksKey drawback
ContiguousFile occupies a single contiguous block rangeExternal fragmentation; hard to grow files
LinkedEach block points to the next (linked list)No efficient random access — must traverse sequentially
IndexedA dedicated index block stores pointers to all data blocksExtra block needed even for small files; multi-level index needed for very large files
Why indexed allocation supports fast random access

Since all block pointers live in one index block, jumping to block k just means reading the k-th pointer directly — no traversal needed, unlike linked allocation where reaching block k requires following k links from the start.

Q2 A file needs random access to its blocks frequently. Which allocation method is least suitable, and why?

Q4 Why does contiguous allocation make it hard to grow a file after creation?

Since the file occupies a single contiguous run of blocks, growing it requires the immediately following blocks to also be free — if they're already allocated to another file, the whole file must be relocated to a larger contiguous space elsewhere.

Answer: Growth requires contiguous free space right after the file, which often isn't available

Maximum blocks addressable = number of pointers = 256. Maximum file size = 256 × 512 bytes = 131072 bytes.

Process states

New→Ready→Running→Terminated, with Running⟷Waiting. Never Waiting→Running directly — always through Ready.

fork() semantics

Returns twice (parent gets child PID, child gets 0). n sequential forks ⟹ 2ⁿ total processes.

Scheduling timings

TAT = Completion − Arrival. WT = TAT − Burst. Response = first CPU allocation − Arrival. Don't confuse WT with TAT.

Scheduling algorithms

SJF minimizes avg WT (non-preemptive optimum, assuming burst times are known in advance). SRTF is its preemptive version. RR fairness depends heavily on quantum size.

Critical section requirements

Mutual Exclusion + Progress + Bounded Waiting — all three required, each independently checkable.

Synchronization mechanisms — lowest to highest level

Peterson's algorithm: pure software, 2 processes only, uses flag[]+turn, busy-waits. Test-and-Set/CAS/Swap: atomic hardware instructions, work for any number of processes, also busy-wait on their own. Semaphore/Mutex: higher-level abstractions usually built on top of a hardware primitive, add blocking instead of pure spinning.

Semaphores

wait(S): S--, block if S≤0. signal(S): S++. A binary semaphore can implement mutual exclusion, but is NOT the same abstraction as a mutex — see the dedicated box below.

Deadlock — 4 necessary conditions

Mutual Exclusion, Hold-and-Wait, No Preemption, Circular Wait. All four required; breaking any one prevents deadlock — see the dedicated box below.

Deadlock vs Starvation

Deadlock: cyclic wait, the blocked set makes zero progress, fixed by breaking a Coffman condition or avoidance. Starvation: no cycle, a process is repeatedly denied while others progress fine, fixed by aging/fair scheduling. Deadlocked ⟹ starving, but not the reverse.

Banker's algorithm

Need = Max − Allocation. "Unsafe" ≠ "deadlocked" — unsafe only means safety can't be guaranteed.

Paging vs Segmentation

Paging: fixed-size, no external fragmentation (internal possible). Segmentation: variable/logical-size, external fragmentation possible.

Contiguous allocation strategies

First Fit: first hole big enough. Best Fit: smallest hole big enough. Worst Fit: largest hole. Next Fit: resume from last position. Best Fit isn't actually best in practice — First Fit performs comparably or better.

Page faults & demand paging

Page fault = trap caused by an invalid/non-resident page-table state; handling may require disk I/O (common case), but not every page fault necessarily does (zero-fill, copy-on-write, other backing mechanisms). TLB miss ≠ page fault (page table lookup is memory-speed). EAT with faults = (1−p)(mem time) + p(fault service time).

TLB & EAT

EAT = h(TLB+Mem) + (1−h)(TLB+2×Mem). TLB hit = 1 memory access; miss = 2 (page table + data).

Page replacement

FIFO can suffer Belady's Anomaly. LRU (stack algorithm) never does. Optimal (OPT/MIN): replaces the page whose next use is farthest in the future — theoretically best, but not implementable online since future references are unknown.

Thrashing & working set

Too many processes → too few frames each → excessive faults → CPU spends most time paging → thrashing. Working set = pages actively referenced in a recent window Δ. If total working-set demand > available frames, thrashing can occur.

IPC — shared memory vs message passing

Shared memory: fast, needs your own synchronization. Message passing (pipes/named pipes/sockets): slower, ordering built in. Signals: async notification only, no real payload.

File metadata & free space

Inode holds metadata + block pointers; directory entry just maps name→inode (hard links share an inode). Free space tracked via bitmap or linked list.

File allocation & disk scheduling

Indexed allocation gives fast random access; linked doesn't. SCAN sweeps like an elevator; C-SCAN services one direction only.

Mutex vs Semaphore — do not treat these as interchangeable

Mutex

  • Ownership-oriented mutual exclusion
  • Only the process/thread that locked it is meant to unlock it
  • A binary locking primitive — no counting

Semaphore

  • Counter-based synchronization primitive
  • Can be binary (0/1) or counting (any non-negative integer)
  • No general ownership requirement — any process can call signal(), even one that never called wait()

A binary semaphore can be used to implement mutual exclusion, which is why it's loosely described as "like a mutex" — but don't let "mutex = binary semaphore" become your final mental model. They are related but not interchangeable abstractions: a mutex enforces ownership by design; a binary semaphore is just a counter capped at 1, with no ownership enforcement built in.

Deadlock — the four Coffman conditions (canonical list)
  1. Mutual exclusion
  2. Hold and wait
  3. No preemption
  4. Circular wait

Deadlock requires all four to hold simultaneously. Breaking any one of them is sufficient to prevent deadlock — this is the single most GATE-tested fact in this topic, and it's exactly why every deadlock-prevention scheme works by attacking just one condition (e.g. requiring all resources upfront breaks Hold-and-Wait; a global resource-ordering rule breaks Circular Wait).

Yes — if a process can never hold some resources while waiting for others (because it must acquire everything at once or nothing), the Hold-and-Wait necessary condition is broken, which prevents deadlock (though it can hurt resource utilization).

Answer: Yes, deadlock is prevented

Q3 Logical address space = 2²⁰ bytes, page size = 2¹⁰ bytes. How many pages exist, and how many offset bits are needed?

Number of pages = 2²⁰/2¹⁰ = 2¹⁰. Offset bits = log₂(page size) = 10 (page number needs the remaining 10 bits of a 20-bit address).

Answer: 1024 pages, 10 offset bits

Q4 A binary semaphore is used for mutual exclusion around a critical section. If initialized to 0 instead of 1, what happens on the first wait() call?

wait(S) blocks while S≤0, and remains blocked until some thread/process performs signal(S) to release a permit. Starting at S=0, the very first process calling wait() blocks immediately since no permit is available yet. In this specific mutual-exclusion setup, that block turns out to be permanent: signal(S) is only ever called after a process has entered and is leaving the critical section, which requires its wait() to have succeeded first — so with no process able to get past wait(), no signal() can ever occur either, and the first entrant deadlocks forever. This is a classic off-by-initialization bug.

Answer: The first process blocks indefinitely — wrong initial value causes immediate deadlock

Q5 Reference string with increasing frame count under LRU never increases page faults. What property guarantees this?

LRU is a "stack algorithm" — the set of pages resident with k frames is always a subset of the set resident with k+1 frames at every point in the reference string, which mathematically forces page faults to be monotonically non-increasing as frames increase.

Answer: The stack property (subset guarantee across frame counts)
