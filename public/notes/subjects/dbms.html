ER Model & Relational Model

ENTITIES & RELATIONSHIPS · KEYS · MAPPING ER TO TABLES · CONSTRAINTS

ER model building blocks

ConstructMeaning
Entitya real-world object with independent existence (e.g. Student)
Weak entityno key of its own — identified only via a owner entity + a partial (discriminator) key
Attributeproperty of an entity: simple, composite, single/multi-valued, derived
Relationshipassociation between entities, with a degree (binary, ternary...) and cardinality (1:1, 1:N, M:N)
Weak entities need identifying relationships

A weak entity (e.g. Dependent, identified only relative to an Employee) is connected to its owner via an identifying relationship, drawn with a double diamond, and the weak entity set is drawn with a double rectangle. Its primary key = owner's key + its own partial/discriminator key.

Types of keys

Candidate key

A minimal superkey — no proper subset of it can also uniquely identify tuples. A relation can have multiple candidate keys.

Primary vs alternate/foreign key

Primary key: the chosen candidate key. Alternate keys: the other candidate keys, not chosen. Foreign key: an attribute referencing a candidate/primary key of another (or the same) relation, enforcing referential integrity.

GATE trap — superkey vs candidate key count

Every candidate key is a superkey, but not every superkey is a candidate key — a superkey can have extra, redundant attributes. If a relation has n attributes and a single-attribute candidate key, the number of superkeys is 2^(n−1) (that attribute must be present; the rest are optional), a classic counting question.

Mapping ER diagrams to relational tables

ER constructTable mapping rule
Strong entityown table, PK = entity's key attribute(s)
Weak entityown table, PK = owner's PK + discriminator; owner's PK is also a FK
1:1 relationshipFK on EITHER side (prefer the side with mandatory participation)
1:N relationshipFK placed on the "N" (many) side, referencing the "1" side's PK
M:N relationshipseparate junction/bridge table with FKs to both entities; together they form its PK
Multi-valued attributeseparate table: FK to owning entity + the attribute value, together forming the PK
GATE trap — total vs partial participation

Total participation (double line in ER diagrams) is an ER-level constraint: every entity instance MUST participate in the relationship. Partial participation (single line) means participation is optional. When the relationship is mapped to tables via a foreign key, total participation is commonly enforced with a NOT NULL constraint on that FK — but this is a mapping choice, not a definitional equivalence: total participation ≠ "NOT NULL" by itself. The exact relational representation depends on the design (e.g. total participation on a weak entity's identifying relationship is enforced structurally, not just via NOT NULL; and a NOT NULL column doesn't by itself tell you an ER relationship was totally participating — it could just be a mandatory attribute). This distinction is frequently tested when mapping 1:1 relationships — the side with total participation is the better place to embed the foreign key, to avoid excess NULLs.

Relational model integrity constraints

  • Domain constraint — each attribute value must come from its declared domain.
  • Entity integrity — no attribute of the primary key can be NULL.
  • Referential integrity — every non-NULL foreign key value must match an existing primary key value in the referenced relation. Whether NULL is permitted at all depends on the FK column's own definition: a nullable FK may hold NULL; one declared NOT NULL (e.g. to enforce total participation) cannot; and a composite FK adds further nuance, since SQL's handling of a key where only some component columns are NULL is implementation/standard-dependent (MATCH FULL / MATCH PARTIAL / MATCH SIMPLE semantics differ).
GATE trap — UNIQUE is not just "a nullable primary key"

Primary key is unambiguous: entity integrity forbids NULL entirely, so a table has at most one row per key value AND no row can leave that column(s) empty.

UNIQUE only enforces that no two non-NULL values in the column are equal — but how many NULLs the column may hold is SQL-semantic / DBMS-dependent, not a single universal rule. The reasoning behind the common (though not universally mandated) behavior: ordinary equality comparisons treat NULL as unknown, so two NULLs are never considered "equal" for a uniqueness check, which is why most SQL implementations (e.g. PostgreSQL, SQL Server, SQLite, MySQL) permit multiple NULLs in a UNIQUE column — but this isn't identical across every system or every reading of the standard, and some configurations restrict it to at most one NULL. Don't memorize "UNIQUE = primary key except nullable" as a universal identity — memorize the actual distinction: primary key forbids NULL outright (entity integrity); UNIQUE only constrains non-NULL values, with NULL-count behavior left to the specific DBMS.

Practice — GATE style (original)

5 questions
Q1 A relation R(A,B,C,D) has candidate key {A}. How many superkeys does R have?

Any superkey must contain the candidate key A. The remaining attributes B, C, D can each independently be included or excluded, giving 2³ = 8 combinations, each unioned with A forming a valid (if sometimes redundant) superkey.

Answer: 8 superkeys

Q2 In an ER diagram, Employee (strong entity) has a 1:1 total-participation-on-both-sides relationship "Manages" with Department. How should this be mapped to tables, and is a separate junction table needed here?

Since both sides have total participation in a 1:1 relationship, the foreign key can be embedded directly in either table (say, dept_id in Employee, or manager_id in Department) without any NULLs on either side — a separate junction table isn't needed here. The standard mapping guideline: 1:N puts the FK on the "N" side; M:N normally requires a junction/associative table since neither side alone can hold multiple FKs cleanly; 1:1 can place the FK on either side. Note this is about what's typically required, not an absolute rule — a designer can still deliberately use a junction table for a 1:1 or 1:N relationship (e.g. to attach relationship-specific attributes, or to keep the schema uniform), even though it isn't structurally necessary.

Answer: Embed the FK directly in either table (no junction table strictly needed for 1:1) — junction tables are the standard requirement for M:N, not the only case they can be used

Q3 Dependent is a weak entity identified relative to Employee via relationship "HasDependent," with Dependent's own partial key being "dep_name". What is Dependent's full primary key in the mapped table?

A weak entity's primary key always combines its owner's full primary key (to disambiguate which owner it belongs to) with its own partial/discriminator key (to disambiguate among that owner's dependents) — since dep_name alone could repeat across different employees' dependents.

Answer: (Employee's PK, dep_name) — the composite of owner's key + discriminator

Q4 Can a foreign key value be NULL? Under what integrity rule, and does this violate referential integrity?

It depends on the FK column's definition. Referential integrity itself only requires that a NON-NULL foreign key value match an existing primary key value in the referenced table — a NULL is treated as "no reference yet" and doesn't violate that rule. But whether NULL is actually allowed is a separate, column-level decision: if the FK is declared NOT NULL (commonly done to enforce total participation from the ER model), NULL is rejected at the column-constraint level, independent of referential integrity.

Answer: Only if the FK column permits NULL (i.e. isn't separately constrained NOT NULL) — referential integrity alone never forbids a NULL FK, only a non-matching non-NULL value would violate it

Q5 A ternary relationship connects entities A, B, and C with cardinality constraints such that each (A,B) pair maps to at most one C. Assume each relationship instance is uniquely identified by its participating entity combination and there are no duplicate relationship instances. How is this typically mapped to a relational table?

A single table is created for the relationship with foreign keys to A, B, and C. Since each (A,B) pair determines at most one C, the primary key of this relationship table can be just (A's key, B's key) rather than all three keys together — reflecting that A and B together are sufficient to identify a unique row. (The uniqueness assumption stated in the question is what rules out the relationship set itself containing duplicate/repeated (A,B,C) instances — without it, "the primary key" wouldn't be well-defined at all, since a relational table's rows must be distinct.)

Answer: One relationship table with FKs to A, B, C; primary key = (A_id, B_id) only, since that pair determines C uniquely

Relational Algebra & Calculus

SELECT/PROJECT/JOIN · SET OPERATIONS · DIVISION · TUPLE & DOMAIN CALCULUS

Core relational algebra operators

OperatorSymbolMeaning
Selectionσcondition(R)filter rows
Projectionπattrs(R)filter columns, removes duplicates
Union / Intersection / Difference∪ ∩ −set ops — require union-compatible relations (same arity, matching domains)
Cartesian productR × Sall combinations of tuples from R and S
Join⋈filtered Cartesian product on a condition
Renameρrenames relation/attributes

Join variants

Natural join (⋈)

Equi-join on ALL commonly-named attributes, then removes the duplicate join columns automatically. If no common attributes exist, natural join degenerates to the Cartesian product.

Theta join (⋈θ)

Join with an arbitrary condition θ (not necessarily equality) — equivalently, σθ(R × S). An equi-join is a theta join restricted to "=" conditions, and unlike natural join, it does NOT auto-remove duplicate columns.

GATE trap — natural join can silently drop rows if column names accidentally match

If R and S share an attribute name that ISN'T semantically meant to be joined on (a coincidental naming collision), natural join will still equate them — potentially producing wrong or empty results. Always verify semantic intent, not just column-name overlap, when reasoning about natural join output.

Division operator — the most-tested RA operator

R ÷ S returns tuples t from R's non-S-attributes such that, for EVERY tuple s in S, the combination (t,s) appears in R. Classic use: "find students who have taken ALL courses in set S."

R(student, course) ÷ S(course) // returns every student who has taken every course listed in S
Division built from primitives (if asked to derive it)
R ÷ S = πX(R) − πX( (πX(R) × S) − R )

Relational calculus

Tuple relational calculus (TRC) — core

{t | P(t)} — t ranges over tuples, P is a formula using t.attribute, ∃, ∀, ∧, ∨, ¬. Declarative — states WHAT to retrieve, not how.

Domain relational calculus (DRC) — supporting

{<x1,...,xn> | P(x1,...,xn)} — variables range over individual domain values (attribute values), not whole tuples.

Prioritization for GATE prep

The official syllabus explicitly names relational algebra, tuple calculus, and SQL — DRC isn't separately listed. Treat TRC as core (understand it well enough to read/write expressions and reason about safety), and DRC as supporting/recognition-level (know what it looks like and how it differs from TRC) unless your own PYQ review turns up enough direct DRC questions to justify deeper drilling.

Expressive equivalence

Relational algebra, TRC, and DRC (restricted to safe expressions, avoiding infinite results from negation over infinite domains) are all provably equivalent in expressive power — this equivalence is called relational completeness, and any of the three can serve as the baseline for judging a query language's power.

Practice — GATE style (original)

5 questions
Q1 R has 5 tuples, S has 3 tuples, both with no attributes in common. How many tuples does R × S produce?

Cartesian product pairs every tuple of R with every tuple of S — the tuple count is the product of the two relation sizes, regardless of attribute overlap (or lack thereof).

Answer: 15 tuples

Q2 Given Enrolled(student, course) and a relation AllCourses(course) listing every course offered, write the RA expression to find students enrolled in every course in AllCourses.

This is the textbook use case for the division operator — dividing the enrollment relation by the full course list returns exactly the students whose enrolled-course set is a superset of (i.e., covers) AllCourses.

Answer: Enrolled ÷ AllCourses

Q3 Why must the operands of a union operation in relational algebra be "union-compatible," and what does that require?

Union combines tuples from two relations into one result set — for that result to be a well-defined relation (fixed number of attributes with consistent domains), both operand relations must have the same number of attributes (arity), and corresponding attributes must draw from compatible domains. Without this, the combined "relation" wouldn't have a consistent schema.

Answer: Same arity and matching attribute domains — needed so the result is itself a well-formed relation

Q4 R(A,B) and S(B,C) are joined with a natural join. R has 4 tuples and S has 3 tuples, and for every tuple of R, exactly one tuple of S has the same B value. How many tuples does R ⋈ S produce?

Natural join matches rows where the shared attribute B agrees. Since every tuple of R has exactly one matching tuple in S (by B value), each of R's 4 tuples contributes exactly one result tuple — no tuple of R is dropped (no match failure) and no tuple of R is duplicated (no multiple matches).

Answer: Exactly 4 tuples

Q5 Explain what "safety" means for a tuple relational calculus expression, and why unsafe expressions are excluded from being considered relationally complete.

A TRC expression is unsafe if it could, in principle, generate an infinite result — most commonly arising from negation combined with an unbounded domain (e.g. "all tuples t such that t is NOT in R" ranges over every possible tuple in an infinite domain). Safety restricts formulas so results are always finite and drawn from values actually appearing in the referenced relations/constants. Only safe TRC expressions are considered when establishing equivalence with relational algebra, since RA itself can never produce an infinite result from finite input relations.

Answer: Safety means the expression can only produce a finite result; unsafe (potentially-infinite) expressions are excluded because RA can never produce infinite output, so only safe TRC is equivalent to it

SQL

QUERY EXECUTION ORDER · JOINS · AGGREGATION · NULL SEMANTICS · SUBQUERIES

Logical order of SQL query evaluation

SQL is written in one order but evaluated in a different logical order — this mismatch is the single most tested SQL concept on GATE. This is the logical (conceptual) query processing order defined by the SQL standard for reasoning about what a query means — it's a model for determining correctness and scoping (what's visible to what), not a claim about the literal sequence of steps a database engine physically executes. A real optimizer is free to reorder, rewrite, or parallelize internally (e.g. pushing a WHERE predicate down, or evaluating subqueries out of this textual order) as long as the final result matches what the logical order would produce. For GATE, always reason in terms of this logical order, not any assumption about physical execution.

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY // written order: SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY

LIMIT/FETCH is not part of the standard logical processing model above — it's dialect- and standard-version-dependent (e.g. MySQL/Postgres LIMIT vs SQL:2008+ FETCH FIRST). When it does apply, it's conceptually the last step, after ORDER BY.

GATE trap — why WHERE can't use aggregate functions but HAVING can

In the logical query processing order (not necessarily the database's actual physical execution steps), WHERE is evaluated before GROUP BY, so no groups (and hence no aggregates like COUNT/SUM) exist yet at that point — using an aggregate in WHERE is a syntax/semantic error. HAVING is evaluated after GROUP BY, when aggregates are available, so it can filter on them. Similarly, a column alias defined in SELECT can't generally be used in WHERE (SELECT runs after WHERE) but often CAN be used in ORDER BY (which runs after SELECT).

Join types and NULL behaviour

JoinUnmatched left rowsUnmatched right rows
INNER JOINdroppeddropped
LEFT OUTER JOINkept, right side NULLdropped
RIGHT OUTER JOINdroppedkept, left side NULL
FULL OUTER JOINkept, right side NULLkept, left side NULL
Worked example — NULL extension in a LEFT JOIN

R(id) = {1, 2}. S(id, val) = {(1, 'x')} — S has no row for id=2.

R LEFT JOIN S ON R.id = S.id: R.id | S.id | S.val -----|------|------ 1 | 1 | 'x' 2 | NULL | NULL

Row 2 from R is preserved even though it has no match in S — every S-side column (including S.id itself, not just S.val) is filled with NULL. This "NULL extension" is exactly what distinguishes LEFT JOIN from INNER JOIN.

GATE trap — a WHERE clause after LEFT JOIN can silently undo it

Adding WHERE S.val = 'x' (or any condition that tests an S-side column with a non-NULL comparison, e.g. S.val = ... or S.id = ...) after the LEFT JOIN above filters row 2 back out, since NULL = 'x' evaluates to UNKNOWN, not TRUE. The query behaves exactly like an INNER JOIN in that case — the whole point of using LEFT JOIN (keeping unmatched left rows) is defeated by a WHERE condition that implicitly requires the right side to be non-NULL. To filter on the right side while still keeping unmatched left rows, the condition needs to explicitly allow the NULL case, e.g. WHERE S.val = 'x' OR S.val IS NULL, or the filter should go in the join's ON clause instead of WHERE.

Three-valued logic and NULL

SQL comparisons involving NULL evaluate to UNKNOWN, not TRUE or FALSE. A WHERE clause only keeps rows where the condition is TRUE — UNKNOWN rows are excluded, same as FALSE ones, but they're logically distinct.

GATE trap — NULL comparisons and NOT IN

x = NULL is always UNKNOWN, never TRUE — must use IS NULL instead. Even more subtle: WHERE x NOT IN (1, 2, NULL) returns zero rows always for ANY x, because NOT IN expands to a chain of AND'd <> comparisons, and x <> NULL is UNKNOWN — ANDing UNKNOWN into the chain poisons the whole condition to never be definitively TRUE.

Prefer NOT EXISTS over NOT IN when the subquery could contain NULLs

The point isn't that NOT EXISTS and NOT IN are universally interchangeable — they aren't, precisely because of the NULL-poisoning trap above. For anti-join semantics (rows in R with no matching row in S) where S's join column might contain NULLs, NOT EXISTS is the safer default, because its correlated subquery compares row-by-row and never builds a flat value list that a stray NULL can silently poison:

WHERE NOT EXISTS ( SELECT 1 FROM S WHERE S.x = R.x )

When S.x has no NULLs, NOT IN (SELECT x FROM S) and this NOT EXISTS form give the same result. The moment S.x can contain NULL, NOT IN silently returns zero rows for everything (as shown above), while NOT EXISTS continues to behave correctly — it only asks "does S.x = R.x hold for any S-row," which is simply FALSE (not UNKNOWN-poisoned) when no match exists, NULLs included.

Aggregate functions and GROUP BY rules

Every column in SELECT that is NOT wrapped in an aggregate function MUST appear in GROUP BY (strict SQL standard) — otherwise the value to display for that column within a group is ambiguous.

COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column) — the canonical distinction
FormCounts
COUNT(*)All rows in the group/table, including rows where every column is NULL
COUNT(column)Only rows where column is non-NULL — NULLs in that column are skipped
COUNT(DISTINCT column)Only the distinct non-NULL values of column — duplicates and NULLs both collapse away

Correlated vs uncorrelated subqueries

Uncorrelated subquery

Independent of the outer query — evaluated once. E.g. WHERE salary > (SELECT AVG(salary) FROM Emp).

Correlated subquery

References a column from the outer query — conceptually re-evaluated once per outer row. E.g. WHERE EXISTS (SELECT 1 FROM Emp e2 WHERE e2.dept=e1.dept AND e2.salary>e1.salary) finds non-top earners per department.

Practice — GATE style (original)

5 questions
Q1 Why does SELECT dept, COUNT(*) FROM Emp WHERE COUNT(*) > 5 GROUP BY dept; fail?

WHERE is evaluated before GROUP BY in the logical query processing order, so no groups (and thus no COUNT(*) per group) exist yet when WHERE runs — aggregate functions are unavailable at that stage. The correct fix is to move the condition to HAVING, which runs after grouping.

Answer: WHERE runs before GROUP BY, so aggregates aren't available yet; must use HAVING COUNT(*) > 5 instead

Q2 Table Emp has 5 rows, 2 of which have dept = NULL. What does SELECT COUNT(dept) FROM Emp; return, versus SELECT COUNT(*) FROM Emp;?

COUNT(column) counts only non-NULL values of that specific column, skipping the 2 NULL depts, giving 3. COUNT(*) counts all rows regardless of NULLs in any column, giving 5.

Answer: COUNT(dept) = 3, COUNT(*) = 5

Q3 Table A(id) has values {1,2,3}. Table B(id) has values {1, NULL}. Under standard SQL three-valued logic, what does SELECT * FROM A WHERE id NOT IN (SELECT id FROM B); return?

SQL uses three-valued logic: every comparison evaluates to TRUE, FALSE, or UNKNOWN, and a row is returned only if the WHERE condition evaluates to TRUE (UNKNOWN is treated like FALSE for filtering, but still "poisons" AND chains differently from FALSE). NOT IN expands to AND-chained inequality checks against every value in the subquery result, including NULL. For any row of A, the comparison "id <> NULL" evaluates to UNKNOWN (not TRUE or FALSE), and ANDing UNKNOWN with anything else (e.g. TRUE AND UNKNOWN → UNKNOWN) can never produce definite TRUE — so the WHERE condition is never satisfied for any row, no matter what id value it has.

GATE trap: this is exactly why NOT IN is dangerous whenever the subquery could return NULLs — NOT EXISTS is the safer default for anti-join logic like this, since it never gets NULL-poisoned this way.

Answer: Empty result (zero rows) — the NULL inside the NOT IN subquery poisons the entire condition under three-valued logic

Q4 Emp(1000 rows) LEFT OUTER JOIN Dept(50 rows) ON Emp.dept_id=Dept.id, where 30 employees have a dept_id that doesn't match any Dept row (including possibly NULL dept_id). How many rows does the result have, at minimum?

LEFT OUTER JOIN preserves every row from the left table (Emp) regardless of whether a match exists on the right (Dept) — unmatched left rows appear once each, with all Dept columns as NULL. So the result has at least all 1000 Emp rows (exactly 1000 if each matching employee matches only one Dept row, since Dept.id being a key means at most one match per employee).

Answer: 1000 rows (every Emp row is preserved; the 30 unmatched ones just get NULL Dept columns)

Q5 Write a correlated subquery to find employees who earn more than the average salary of their OWN department (not the company-wide average).

Because "average of their own department" depends on which department the outer row belongs to, the subquery must reference the outer query's department value — making it correlated (re-evaluated conceptually per outer row) rather than a single company-wide average computed once.

Answer: SELECT * FROM Emp e1 WHERE salary > (SELECT AVG(salary) FROM Emp e2 WHERE e2.dept_id = e1.dept_id);

Functional Dependencies & Normalization

ARMSTRONG'S AXIOMS · CLOSURE & CANDIDATE KEYS · 1NF–BCNF · DECOMPOSITION PROPERTIES

Functional dependency basics

X → Y means: whenever two tuples agree on X, they must also agree on Y. X is the determinant, Y is the dependent.

Armstrong's axioms (sound & complete)
  • Reflexivity: if Y ⊆ X, then X → Y
  • Augmentation: if X → Y, then XZ → YZ
  • Transitivity: if X → Y and Y → Z, then X → Z

Derived rules (union, decomposition, pseudotransitivity) all follow from these three.

Computing attribute closure (X⁺)

The single most-tested computational skill in this module: given a set of FDs, compute X⁺ (all attributes functionally determined by X) by repeatedly applying FDs whose LHS is already covered, until no more attributes can be added.

GATE trap — using closure to test candidate keys

X is a candidate key of R iff X⁺ = all attributes of R, AND no proper subset of X also has this property (minimality). GATE routinely asks "compute X⁺" as a stepping stone to "is X a candidate key / superkey" or "does X → Y hold" (check if Y ⊆ X⁺).

Normal forms — what each one actually forbids

FormRequires (in addition to previous)
1NFatomic (indivisible) attribute values — no repeating groups or multi-valued cells
2NFno partial dependency — every non-prime attribute fully depends on the WHOLE of every candidate key (only matters when a key is composite)
3NFfor every non-trivial FD X→A: X is a superkey, OR A is a prime attribute (part of some candidate key) — informally, "no transitive dependency," but that phrase is a mnemonic, not the formal test
BCNFfor EVERY non-trivial FD X→Y, X must be a superkey — stricter than 3NF, drops 3NF's escape clause
The formal 3NF definition — and why "no transitive dependency" alone is dangerous

The GATE-precise definition of 3NF is: for every non-trivial FD X → A in R, either X is a superkey of R, or A is a prime attribute. "No transitive dependency" is a useful intuition for the first disjunct, but stated on its own it's incomplete — it hides the second disjunct (the prime-attribute escape clause) that GATE questions routinely exploit. A relation can have what looks like a transitive dependency (A determines B, B determines C) and still be in 3NF, as long as C happens to be part of some candidate key. Always check primeness before concluding a violation.

This escape clause is exactly what BCNF removes: 3NF allows a non-superkey X → Y dependency IF Y is a prime attribute — this exception is what makes 3NF always achievable via lossless, dependency-preserving decomposition, unlike BCNF, which sometimes must sacrifice dependency preservation to remain lossless.

Decomposition properties

Lossless-join decomposition

For a decomposition of R into R1, R2 governed by FD set F, it is lossless iff (R1∩R2) → R1 or (R1∩R2) → R2 holds in F⁺ (the closure of F) — not just among the FDs literally listed, but among everything derivable from them. The common attributes must be a key (or superkey) of at least one of the two pieces; testing this properly means computing (R1∩R2)⁺ under F, not merely scanning F's given FDs by eye.

Dependency-preserving decomposition

Every original FD can be verified using only FDs local to individual decomposed relations (no need to rejoin them to check). BCNF decomposition sometimes cannot preserve all original dependencies — a fundamental tradeoff GATE tests directly.

Practice — GATE style (original)

5 questions
Q1 R(A,B,C,D) has FDs: A→B, B→C, C→D. Compute A⁺.

Start with {A}. A→B adds B: {A,B}. Now B→C applies (B is covered): add C: {A,B,C}. Now C→D applies: add D: {A,B,C,D}. No more FDs apply — closure is complete and covers all of R's attributes.

Answer: A⁺ = {A,B,C,D} — so A is a candidate key of R

Q2 R(A,B,C) has candidate key {A,B} and FD: B→C (a non-prime attribute C depends on part of the composite key, not all of it). Which normal form does R violate?

C is a non-prime attribute (not part of any candidate key) and it depends only on B, which is a PROPER SUBSET of the composite candidate key {A,B} — this is exactly the definition of a partial dependency, which 2NF forbids.

Answer: Violates 2NF (partial dependency of non-prime C on part of the composite key)

Q3 R(A,B,C) has candidate key {A} and FD chain A→B, B→C, where C is non-prime. Is R in 3NF? Is it in BCNF?

By the formal test (for every non-trivial FD X→A: X is a superkey, or A is a prime attribute), check the FD B→C: B is not a superkey (the only candidate key is {A}), and C is non-prime, so this FD satisfies neither disjunct — the escape clause doesn't save it. So R violates 3NF. (Informally, this shows up as C depending on A only transitively, through B — "transitive dependency of a non-prime attribute" is a useful intuition for this case, but the formal test above is what actually decides it, since a transitive-looking chain can still be fine in 3NF if the final attribute happens to be prime.) Since BCNF is stricter than 3NF (BCNF ⇒ 3NF), the contrapositive holds: violating 3NF automatically means violating BCNF too.

Answer: R violates both 3NF (transitive dependency A→B→C) and consequently BCNF too

Q4 R(A,B,C) is decomposed into R1(A,B) and R2(B,C). Given FD B→C holds in R, is this decomposition lossless?

The common attribute between R1 and R2 is B. Lossless-join requires (R1∩R2)→R1 or (R1∩R2)→R2 to hold in F⁺ (the closure of the given FD set) — i.e. B→(A,B) or B→(B,C) must be derivable, not necessarily listed outright. Compute B⁺ under F: B→C is given, and B→B holds trivially by reflexivity, so B⁺ ⊇ {B,C}, meaning B→(B,C) is in F⁺ — satisfying the lossless-join condition via the second disjunct.

Answer: Yes, lossless — because B→BC is derivable in F⁺ (from the given B→C plus trivial reflexivity), satisfying the lossless-join test

Q5 Why can BCNF decomposition sometimes fail to be dependency-preserving, while the standard 3NF synthesis algorithm always guarantees it?

BCNF requires every non-trivial FD's LHS to be a superkey, with NO exceptions — so if an FD X→Y exists where X is not a superkey but Y happens to be prime (part of some other candidate key), BCNF still forces you to decompose it away, and that FD may end up spanning two separate decomposed relations with no single relation able to verify it locally. 3NF explicitly permits exactly this situation (its "Y is prime" escape clause), which is precisely why the 3NF synthesis algorithm can always guarantee both losslessness AND dependency preservation simultaneously, while BCNF decomposition cannot always guarantee both together. Note this guarantee is specific to the standard 3NF synthesis algorithm (built from a minimal cover of the FDs) — it doesn't mean every arbitrary decomposition into 3NF relations is automatically dependency-preserving.

Answer: The standard 3NF synthesis algorithm can guarantee dependency preservation, whereas BCNF decomposition may sacrifice it — BCNF has no escape clause for FDs whose RHS is prime, so decomposing to satisfy BCNF can split such an FD across relations and lose the ability to check it locally

Transactions, Concurrency Control & Recovery

ACID · SCHEDULES, SERIALIZABILITY & RECOVERABILITY · 2PL & TIMESTAMP ORDERING · DEADLOCK · UNDO/REDO RECOVERY

ACID properties

PropertyGuarantees
Atomicitya transaction executes fully or not at all (no partial effects survive)
Consistencya transaction moves the DB from one valid state to another, preserving all declared constraints
Isolationconcurrently executing transactions behave as if appropriately separated from each other's effects — serializability is the classical theoretical goal; the exact guarantee depends on the isolation level in force
Durabilityonce committed, changes survive any subsequent crash
Isolation isn't just "no dirty reads"

Isolation as an ACID property is about concurrent execution being equivalent to some serial execution (serializability), not a specific promise that no transaction ever sees another's uncommitted data. SQL isolation levels intentionally trade this off: READ UNCOMMITTED permits dirty reads by design, while READ COMMITTED and stronger levels prevent them. Don't equate "isolation" with "no dirty reads" — dirty-read prevention is one phenomenon controlled by isolation level, not the definition of isolation itself.

Schedules and serializability

Conflict serializability

A schedule is conflict-serializable if it can be transformed into a serial schedule by repeatedly swapping adjacent, non-conflicting operations (from different transactions). Tested via the precedence graph: draw an edge Ti→Tj if Ti has an operation that conflicts with and precedes a later operation of Tj on the same data item — the schedule is conflict-serializable iff this graph is acyclic.

View serializability

A strictly weaker/broader condition — equivalent in initial reads, final writes, and which transaction's write each read sees. Every conflict-serializable schedule is view-serializable, but NOT vice versa (view-serializable schedules can exist that aren't conflict-serializable, typically involving "blind writes").

GATE trap — precedence graph cycle detection

To build the precedence graph, only consider pairs of operations from DIFFERENT transactions on the SAME data item where at least one is a write (RW, WR, or WW conflicts — RR is not a conflict since reads don't interfere). If the resulting graph has ANY cycle, the schedule is NOT conflict-serializable, no matter how few edges are involved.

Worked example — a schedule that IS view-serializable but is NOT conflict-serializable

Three transactions on a single data item Q: T1 reads then writes Q; T2 and T3 each perform a single "blind write" to Q (a write with no prior read in that transaction). Schedule S:

S: R1(Q) W2(Q) W1(Q) W3(Q)

Step 1 — build the precedence graph. Compare every pair of conflicting operations (different transactions, same item, at least one write) in the order they occur in S:

  • R1(Q) before W2(Q) → RW conflict → edge T1 → T2
  • W2(Q) before W1(Q) → WW conflict → edge T2 → T1
  • W1(Q) before W3(Q) → WW conflict → edge T1 → T3
  • W2(Q) before W3(Q) → WW conflict → edge T2 → T3

The edges T1→T2 and T2→T1 form a 2-cycle by themselves — the precedence graph is cyclic, so S is NOT conflict-serializable, full stop (no serial schedule is reachable from S by swapping adjacent non-conflicting operations).

Step 2 — check view-serializability directly (the three conditions), independent of the graph. (a) Same initial reads: only T1 reads Q, and in S it reads before any write — so any view-equivalent serial order must also have T1 read Q first, meaning T1 must run before T2 and T3. (b) Same "reads-from" for every read: there's only one read (T1's), already satisfied by (a) — no other transaction reads a value written by another. (c) Same final write: in S, the last write to Q is W3(Q) — so T3 must also write last in the serial order. These three constraints force exactly one candidate order: T1, T2, T3.

Step 3 — verify T1,T2,T3 as a serial schedule matches all three conditions. T1 reads the initial value of Q (nobody wrote before it) ✓. No transaction reads a value written by another transaction in either S or the serial order (T2 and T3's writes are never read by anyone) ✓. The final write to Q is T3's in both S and the serial order ✓. All three view-equivalence conditions hold, so S IS view-serializable (view-equivalent to the serial schedule T1, T2, T3).

Result: S is view-serializable (≡ T1,T2,T3) but not conflict-serializable (cyclic precedence graph) — exactly the gap the "Conflict-serializable ⊂ View-serializable" containment describes. The gap exists here specifically because T2's and T3's blind writes create conflict edges that force an ordering the conflict-equivalence swap rules can't realize, even though the schedule's overall external effect (what's read, what Q ends up as) is indistinguishable from a valid serial execution.

Schedule recoverability — a separate axis from serializability

Serializability asks "is this schedule equivalent to some serial order?" Recoverability asks a different question: "if a transaction aborts, can the system actually undo its effects cleanly?" A schedule can be serializable and still be unrecoverable — these are independent properties GATE tests separately.

ClassRuleRelationship
RecoverableTi commits only after every Tj it read an uncommitted value from has already committedWeakest — just avoids permanently-uncorrectable states
Cascadeless (avoids cascading rollback)Every transaction reads only values written by already-committed transactions (no dirty reads at all)Stronger than recoverable — every cascadeless schedule is recoverable, not vice versa
StrictA transaction can neither read NOR overwrite a data item written by another transaction until that writer commits/abortsStrongest — every strict schedule is cascadeless (and hence recoverable); strict 2PL guarantees this
Nesting to remember

Strict ⊂ Cascadeless ⊂ Recoverable ⊂ (all schedules). GATE frequently gives a schedule and asks which of these classes it belongs to — check strict first (fails fast if any dirty read/write exists), then cascadeless, then recoverable, since each stronger class automatically satisfies the weaker ones.

GATE trap — the read vs write distinction that separates cascadeless from strict

Students commonly conflate cascadeless and strict because both talk about "not touching uncommitted data" — the precise difference is exactly which operation is restricted:

ClassRestricts reads of uncommitted writes?Restricts overwrites of uncommitted writes?Rule of thumb
RecoverableAllowed, but the reader (Tj) can't commit before the writer (Ti) it read from commitsAllowed, no restrictionIf Tj reads from Ti, Ti must commit before Tj
CascadelessForbidden — a transaction may never read a value written by an uncommitted transaction (no dirty reads at all)Allowed, no restrictionTransactions never read uncommitted data
StrictForbidden (same as cascadeless)Also forbidden — a transaction may not even overwrite (blind-write over) a value written by an uncommitted transaction until it commits/abortsTransactions cannot read OR overwrite an item written by an uncommitted transaction

So cascadeless only closes the door on reading dirty data; strict additionally closes the door on writing over dirty data before the original writer resolves. A schedule can be cascadeless yet still allow one transaction to blindly overwrite another's uncommitted write — that schedule is cascadeless but not strict, exactly the trap GATE sets up.

Locking protocols

Two-Phase Locking (2PL): every transaction has a growing phase (only acquires locks) followed by a shrinking phase (only releases locks) — once a lock is released, no new lock can be acquired. 2PL guarantees conflict-serializability but does NOT by itself prevent deadlock or cascading rollback.

Strict 2PL

Holds ALL exclusive (write) locks until commit/abort (not just until the shrinking phase begins) — this additionally prevents cascading rollback, since no other transaction can read an uncommitted write. Strict 2PL is the most commonly assumed protocol in GATE problems unless stated otherwise.

GATE trap — Basic 2PL vs Strict 2PL vs Rigorous 2PL

All three enforce the same growing/shrinking-phase discipline, but they differ in exactly when locks are released — and that difference is what each protocol additionally buys you:

ProtocolLock-release ruleGuarantees
Basic 2PLLocks may start being released as soon as the shrinking phase begins — a lock can be released well before commit/abort, as long as no new lock is acquired afterwardConflict-serializability only — does NOT prevent cascading rollback (a released write lock lets others read uncommitted data)
Strict 2PLAll exclusive/write locks are held until commit/abort; shared/read locks may still follow ordinary 2PL release timingConflict-serializability + avoids cascading rollback (nobody can read an uncommitted write)
Rigorous 2PLAll locks — both shared/read and exclusive/write — are held until commit/abortConflict-serializability + avoids cascading rollback, with the added property that transactions appear to execute in exactly their commit order (strictly serializable) — the strongest of the three

Mnemonic: Basic 2PL only constrains WHEN locks can be released relative to each other (growing vs shrinking phase); Strict 2PL pins write-lock release to commit time specifically; Rigorous 2PL pins ALL lock release to commit time. GATE options often swap "read locks" and "write locks" between Strict and Rigorous to test whether you know which one holds only exclusive locks vs all locks until commit.

Timestamp ordering — an alternative to locking

Instead of locks, every transaction Ti is assigned a unique timestamp TS(Ti) at start (typically its start time or a monotonic counter) — older transactions get smaller timestamps. Every data item Q tracks two values: W-timestamp(Q) (largest timestamp of any transaction that successfully wrote Q) and R-timestamp(Q) (largest timestamp of any transaction that successfully read Q). Conflicts are resolved by comparing these to the requesting transaction's timestamp, rejecting (and rolling back) any operation that would violate timestamp order.

Basic timestamp-ordering protocol, for transaction Ti requesting on item Q: READ(Q): if TS(Ti) < W-timestamp(Q): reject, rollback Ti [Ti is too old — would read a value "from the future"] else: allow read; R-timestamp(Q) = max(R-timestamp(Q), TS(Ti)) WRITE(Q): if TS(Ti) < R-timestamp(Q): reject, rollback Ti [a younger transaction already read Q — this write would undo that read's validity] else if TS(Ti) < W-timestamp(Q): reject, rollback Ti (or, under Thomas Write Rule, just IGNORE the write instead of rolling back) else: allow write; W-timestamp(Q) = TS(Ti)
Thomas Write Rule — the one refinement GATE likes to test

Basic timestamp ordering rolls back Ti whenever TS(Ti) < W-timestamp(Q) on a write. The Thomas Write Rule relaxes this specific case: if TS(Ti) < W-timestamp(Q), the write is simply ignored (not applied) rather than rolling back Ti, because a later transaction has already overwritten Q with a "newer" value that will win anyway — this is safe precisely because no one read the value Ti was about to write. Thomas Write Rule allows some schedules that are view-serializable but NOT conflict-serializable to still be permitted (it's not equivalent to conflict-serializability).

GATE trap — timestamp ordering guarantees conflict-serializability automatically

This guarantee is specific to basic timestamp ordering (the algorithm above without the Thomas Write Rule). Unlike 2PL, basic TO never causes deadlock (transactions are simply rolled back on conflict, never made to wait for each other), but it can cause more aborts/rollbacks in practice. Basic TO guarantees a conflict-serializable schedule equivalent to the timestamp order itself — but does NOT automatically guarantee recoverability; a separate mechanism (e.g. only allowing commits after all read-from transactions commit) is needed for that.

Once the Thomas Write Rule is introduced, this specific guarantee changes: as noted above, Thomas Write Rule permits some schedules that are view-serializable but not conflict-serializable, so "conflict-serializable equivalent to timestamp order" no longer holds unqualified — the correct claim under Thomas Write Rule is the weaker one, view-serializability. Unless a question specifies Thomas Write Rule, assume basic timestamp ordering is what's being tested.

Deadlock — detection and prevention

The general framework — four categories, don't conflate them
TechniqueIdea
PreventionStructurally rule out one of the four necessary conditions for deadlock (mutual exclusion, hold-and-wait, no preemption, circular wait) so deadlock can never arise in the first place
AvoidanceAllow requests dynamically, but before granting one, check whether the resulting system state is still "safe" (some ordering exists in which all transactions can finish) — deny/delay the request if it isn't
DetectionDon't restrict anything up front — let deadlock potentially happen, then periodically check for it and react
RecoveryOnce a deadlock is detected, break it: abort one or more transactions, or preempt (forcibly take) a resource, or roll back to a safe point

Where the standard DBMS techniques map onto this framework:

  • Wait-die / Wound-wait → Prevention. Both work by imposing a strict ordering rule (based on transaction age/timestamp) on who is allowed to wait for whom, which structurally rules out circular wait — the deadlock condition these two schemes specifically target.
  • Banker's Algorithm → Avoidance. It's the canonical avoidance technique (more commonly taught in the OS context of resource allocation, but the same safe-state-checking idea applies conceptually to transaction resource requests): grant a request only if the resulting allocation state is still safe.
  • Wait-for graph cycle detection → Detection. Transactions are allowed to wait freely; the DBMS periodically builds a wait-for graph and checks for cycles, only reacting once one is found.
  • Aborting the "victim" transaction once a wait-for cycle is found is the Recovery step that follows detection.
ApproachMechanism
Prevention (wait-die)older transaction waits for younger; younger requesting a lock held by older is aborted (dies)
Prevention (wound-wait)older transaction "wounds" (forces abort of) younger holder; younger waits for older
Detectionbuild a wait-for graph; a cycle indicates deadlock — abort a victim to break it

Recovery — update strategies

How a DBMS handles writes relative to when they hit the log vs the actual database determines what recovery must do after a crash. The two classic strategies:

StrategyWhen DB is actually updatedRecovery needs
Deferred updateOnly after the transaction commits (all writes are buffered/logged first, applied to disk at commit)REDO only — since nothing uncommitted ever reached disk, there's nothing to undo; just re-apply committed transactions' writes if they didn't make it to disk before the crash
Immediate updateWrites can be applied to disk as soon as they happen, even before commitNeeds both UNDO (for transactions that didn't commit — their partial writes may already be on disk and must be reversed) and REDO (for committed transactions whose writes might not have reached disk yet)

UNDO / REDO — what each actually does

UNDO

Reverses the effect of a write using the log's before-image (old value) — applied to transactions that were active (uncommitted) at crash time, so their partial effects are removed entirely, preserving atomicity.

REDO

Re-applies a write using the log's after-image (new value) — applied to transactions that had committed but whose writes might not have made it from buffer to disk before the crash, so their effects are guaranteed durable.

UNDO/REDO — the general case

A DBMS supporting both immediate update and checkpointing typically needs an UNDO/REDO recovery algorithm: scan the log backward from the crash point to identify committed vs uncommitted transactions, UNDO all writes of transactions that never committed, and REDO all writes of transactions that did commit (to guarantee durability even if their writes hadn't yet reached disk).

Recovery from the log after a crash — the standard procedure

  1. Scan the log backward from the end (crash point), building the set of transactions found.
  2. A transaction is committed if a <commit T> record appears in the log for it — its writes must be REDONE (durability).
  3. A transaction is uncommitted (active at crash, or explicitly aborted) if no <commit T> record exists — its writes must be UNDONE (atomicity).
  4. If checkpoints exist, recovery only needs to scan back to the most recent checkpoint's transaction list, not the entire log history — checkpointing exists precisely to bound this scan.
  5. Apply UNDOs and REDOs (order matters in some schemes — e.g. UNDO in reverse chronological order, REDO in forward chronological order — to correctly reconstruct the final consistent state).

Worked example — tracing a crash against the log

Log (in order written), with a checkpoint in the middle: <T0 start> T0: W(X) <T0 commit> <CHECKPOINT> (active-transaction list at this point: { } — T0 already committed) <T1 start> T1: W(A) <T2 start> T2: W(B) <T1 commit> *** CRASH ***
Reading the trace — step by step

1. Where recovery starts scanning: from the crash point, scan backward only to the most recent CHECKPOINT — not the entire log. Anything before the checkpoint (here, T0) is already known-consistent on disk and needs no redo/undo work re-examined; that's the entire point of checkpointing.

2. Transactions active after the checkpoint: T1 and T2 both started after the checkpoint, so both must be classified using the log between the checkpoint and the crash.

3. Classify each: T1 has a <commit T1> record → its write W(A) must be REDONE (using the after-image of A), to guarantee durability in case A hadn't reached disk before the crash. T2 has no commit record (still active at crash) → its write W(B) must be UNDONE (using the before-image of B), to preserve atomicity — none of T2's partial effect may survive.

4. T0's status: T0 committed before the checkpoint was even taken, so it needs no action at all during this recovery — this is exactly what makes checkpointing valuable: T0's work is irrelevant to the crash-time analysis.

Result: REDO {T1's W(A)}, UNDO {T2's W(B)}, T0 untouched (already safe before the checkpoint).

Recovery — logging protocols

WAL (Write-Ahead Logging)

The log record for a change must be written to stable storage BEFORE the corresponding data page is written to disk — this is what makes crash recovery (undo/redo) possible at all.

Checkpointing

Periodically records which transactions are active, limiting how far back the recovery process must scan the log after a crash — without it, recovery would need to replay the entire log history.

Practice — GATE style (original)

5 questions
Q1 A schedule's precedence graph has edges T1→T2, T2→T3, T3→T1. Is the schedule conflict-serializable?

These three edges form a cycle (T1→T2→T3→T1). Conflict-serializability requires an acyclic precedence graph — a cycle directly proves the schedule cannot be reordered into any equivalent serial schedule.

Answer: No, not conflict-serializable (the precedence graph has a cycle)

Q2 Does two-phase locking (2PL) guarantee freedom from deadlock merely because the schedules it produces are conflict-serializable? Explain.

No — conflict-serializability is a property of a completed schedule (the actual order operations ended up executing in), evaluated after the fact. Deadlock is a runtime lock-acquisition hazard that can occur while transactions are contending for locks, potentially preventing any schedule from ever completing at all — 2PL guarantees that whatever schedule DOES complete is conflict-serializable, but doesn't by itself prevent transactions from deadlocking while trying to acquire locks in the first place.

Answer: No — 2PL guarantees conflict-serializability of completed schedules, but does not itself prevent deadlock during execution

Q3 Under the wait-die deadlock prevention scheme, an older transaction Ti requests a lock held by younger transaction Tj. What happens?

Wait-die's rule: an older transaction is allowed to WAIT for a younger one to release its lock (it doesn't "die"). It's the reverse situation — a younger transaction requesting a lock held by an older one — that causes the younger requester to be aborted ("dies").

Answer: Ti (older) waits for Tj (younger) to release the lock — no abort occurs in this direction under wait-die

Q4 Why does strict 2PL prevent cascading rollback, while ordinary (non-strict) 2PL does not?

Cascading rollback happens when transaction Tj reads a value written by Ti, and Ti later aborts — forcing Tj (and anything that read from Tj) to also roll back. Ordinary 2PL only guarantees locks aren't newly ACQUIRED after the shrinking phase begins, but write locks can still be released (and hence read by others) before commit. Strict 2PL holds all write locks until commit/abort, so no other transaction can ever read an uncommitted (potentially-to-be-aborted) write in the first place — eliminating the possibility of cascading rollback entirely.

Answer: Strict 2PL holds write locks until commit, so nobody can read uncommitted data — removing the precondition for cascading rollback

Q5 Why must the write-ahead log record be flushed to stable storage BEFORE the corresponding modified data page is written to disk?

If the data page were written first and the system crashed before the log record was saved, there would be no record describing what changed — making it impossible to undo that change if the transaction later needs to be rolled back, or to redo it correctly if only partially applied. Writing the log first guarantees that, no matter when a crash occurs, the log always has enough information to recover the data page to a consistent state (undo or redo) matching what actually happened.

Answer: So that recovery always has a log record describing any change that might have reached disk, enabling correct undo/redo after a crash regardless of when it occurred

Practice — Recoverability, Timestamp Ordering & UNDO/REDO (original)

4 questions
Q1 Schedule S: T2 reads a value written by T1; T1 commits AFTER T2 already commits. Is S recoverable?

Recoverability requires that if Tj reads a value written by Ti, Ti must commit BEFORE Tj commits. Here T2 (the reader) commits before T1 (the writer it read from) — so if T1 later aborts instead of committing, T2's already-committed read would be uncorrectable. This violates recoverability.

Answer: No, S is not recoverable — the reader (T2) committed before the writer it depended on (T1)

Q2 Transaction Ti has TS(Ti)=5. Data item Q currently has W-timestamp(Q)=8. Under basic timestamp ordering, what happens if Ti attempts to write Q? What changes under the Thomas Write Rule?

Basic TO: since TS(Ti)=5 < W-timestamp(Q)=8, a newer transaction has already written Q — Ti's write is rejected and Ti is rolled back. Under the Thomas Write Rule, this specific case (TS(Ti) < W-timestamp(Q), no younger read to violate) instead just ignores/skips Ti's write silently — Ti continues without rollback, since its write would immediately be overwritten anyway.

Answer: Basic TO rolls back Ti; Thomas Write Rule instead ignores the write and lets Ti proceed

Q3 A system uses deferred update. A transaction crashes before committing. Does recovery need to UNDO anything on disk for it?

No — under deferred update, writes are only applied to the actual database after commit. Since this transaction never committed, none of its writes ever reached disk in the first place, so there's nothing to undo — recovery simply discards its log records.

Answer: No UNDO needed — deferred update guarantees uncommitted writes never reached disk

Q4 During log-based recovery after a crash, the log shows: T1 has <commit T1>, T2 has no commit record. What recovery action applies to each?

T1 committed, so its writes must be REDONE (using after-images) to guarantee durability in case they hadn't reached disk before the crash. T2 never committed, so its writes must be UNDONE (using before-images) to preserve atomicity — none of its partial effects should survive.

Answer: T1 → REDO; T2 → UNDO

Indexing & File Organization

ORDERED/HASH FILES · PRIMARY VS SECONDARY INDEX · B/B+ TREES · SPARSE VS DENSE

File organization strategies

OrganizationAccess pattern
Heap (unordered)fast insert (append), slow search — O(n) scan
Sequential (ordered)fast range queries, but insert/delete requires reorganization or overflow areas
Hashfast exact-match lookup — O(1) average, but no support for range queries

Primary vs secondary index — defined by the DATA FILE's order, not the index itself

The classification below follows the classical file-organization terminology used in GATE/DBMS textbooks (Silberschatz-style) — it's a standard, widely-taught model, but treat it as that specific classical framework rather than a universal property every real-world database implementation is bound to.

Primary index

Built on the field that the data file is physically sorted by (usually the key). Can be sparse.

Secondary index

Under this same classical terminology: built on a field that does NOT determine the data file's physical order. Must always be dense, since consecutive index entries don't correspond to physically adjacent records.

GATE trap — "primary index" and "clustered index" are not synonyms

These two terms answer genuinely different questions, and it's easy to blur them together:

  • Primary index is defined relative to WHICH KEY the index is built on and searches by — an index whose search key is the ordering key the file is defined to be sorted on (in most textbook treatments used for GATE, this is the relation's primary key).
  • Clustered index is defined relative to PHYSICAL STORAGE — it means the data records THEMSELVES are physically stored/ordered according to that index's key, whatever that key happens to be.

In the standard textbook examples used for GATE, a table's primary index and its clustered index usually coincide — the file is kept sorted by the primary key, so the primary index is also the clustered one. But they are not interchangeable by definition: a real DBMS can build a clustered index on a non-primary-key column (any single column the physical rows get sorted by), and conceptually "primary" describes the choice of key while "clustered" describes the physical row ordering. Only one clustered index can exist per table (data can only be physically sorted one way at a time); a table can have many non-clustered (secondary) indexes alongside it.

Index typeTypical property
DenseIndex entry for every search-key value / record
SparseEntries for only some search-key values / blocks
GATE trap — sparse index requires the file to be sorted on that field

A sparse index has one entry per BLOCK (not per record) — it only works if the file is physically sorted by the indexed field, so the index can point to a block and a sequential scan within that block finds the target. Sparse indexing therefore generally requires the underlying data file to be ordered on the search key — which is exactly why a sparse index is always a primary/clustering index; a secondary index can never be sparse, because the data file isn't ordered by the secondary key.

Dense index

One entry for EVERY record (or every distinct key value, for a duplicate-key field), regardless of file ordering — works on both primary and secondary indexes, but uses more storage than sparse.

B-Tree vs B+-Tree — the most-tested distinction

B-TreeB+-Tree
Data pointersin BOTH internal and leaf nodesONLY in leaf nodes
Leaf nodesnot linkedlinked in a sequence (linked list) — enables fast range scans
Key redundancyeach key stored exactly onceinternal-node keys are duplicated as "guide posts"; actual data reference lives in the leaf
Fan-outlower (data pointers take space in internal nodes)higher (internal nodes hold only keys, so more fit per node)
GATE trap — why B+-trees are preferred for DBMS indexes

Because B+-tree internal nodes store ONLY keys (no data pointers), they achieve a much higher fan-out per node than a B-tree of the same node/block size — this means fewer levels for the same number of keys, i.e. fewer disk I/Os per search. Combined with the linked leaf list enabling efficient range queries (just walk the leaf chain), this is why virtually every real DBMS uses B+-trees, not plain B-trees, for indexing.

The 3-line canonical comparison (memorize this exact framing)

B-tree: keys/records can potentially appear in internal nodes as well as leaves — a search can terminate early at an internal node if the key is found there.

B+-tree: actual records/data pointers are stored ONLY at the leaves; internal nodes store nothing but separator/guide keys used purely to route the search — every search always descends all the way to a leaf, even for keys that appear "early."

B+-tree leaves are linked (leaf-to-leaf pointers) → efficient sequential/range traversal without re-traversing the tree; plain B-trees have no such linkage.

B-Tree / B+-Tree order and height calculations

For a B+-tree of order p (max p pointers per node): each internal node holds at most p−1 keys and p pointers, at least ⌈p/2⌉ pointers (except root). GATE frequently asks you to compute the maximum number of records searchable in h levels, or the minimum height for n records, given a fan-out.

B+-Tree deletion — the part revision sheets usually skip

Deletion is the mirror image of insertion: instead of a node overflowing and splitting, a node can underflow (drop below the minimum ⌈p/2⌉ occupancy) and needs to borrow from or merge with a sibling. Steps, at a glance:

  1. Delete from the leaf: locate the key via a normal search, remove it (and its data pointer) from the leaf node.
  2. Check for underflow: if the leaf still meets the minimum occupancy (⌈p/2⌉ pointers/keys), deletion is done — no further action needed.
  3. If underflow occurs, try redistribution (borrowing) first: check an immediate sibling (left or right) that has MORE than the minimum — if one exists, move one key/pointer over from that sibling into the underflowing node, and update the separator key in the parent to reflect the new split point.
  4. If no sibling can spare a key, merge instead: combine the underflowing node with a sibling into one node (which will still satisfy the max-occupancy bound, since together they held at most one node's worth plus the borrowed minimum), and remove the now-unused separator key from the parent.
  5. Propagate upward if needed: removing a separator key from the parent (step 4) can itself cause the parent to underflow — the same redistribute-or-merge logic then applies one level up, potentially cascading all the way to the root. If the root ends up with only one child after a merge, that child becomes the new root (tree height decreases by one).
GATE trap — redistribution vs merge, and the parent separator update

Always prefer redistribution over merging when a sibling has a spare key to lend — it's cheaper (no restructuring, no possible cascade upward) and keeps the tree shallower on average. Merging is only used when redistribution isn't possible (both adjacent siblings are already at minimum occupancy). Either way, the parent's separator key MUST be updated: redistribution shifts the separator to reflect the new dividing key between the two nodes; merging removes the separator entirely, since the two children have become one.

Practice — GATE style (original)

5 questions
Q1 Can a secondary index ever be sparse? Justify.

A sparse index relies on the data file being physically sorted by the indexed field, so one index entry per block is enough — a sequential scan within that block finds the target record. A secondary index is, by definition, built on a field the data file is NOT sorted by, so consecutive records with the indexed value aren't guaranteed to be in the same block — a sparse secondary index simply couldn't locate records reliably.

Answer: No — sparse indexes require the file to be sorted on the indexed field, which is precisely what a secondary index is not

Q2 Which structure supports efficient range queries better — B-Tree or B+-Tree — and why specifically?

B+-Tree, because its leaf nodes are linked together in a sequential chain — once you find the starting key via a single root-to-leaf traversal, you can retrieve the rest of the range simply by following leaf-to-leaf pointers without any further tree traversal. A plain B-Tree has no such leaf linkage, so a range scan may require repeated in-order traversal logic across the tree structure itself.

Answer: B+-Tree — its linked leaf-node chain allows sequential range retrieval without re-traversing the tree

Q3 A B+-tree of order 4 (max 4 pointers per node, 3 keys per node) has a height of 3 (root + 2 levels, root itself considered level 1, leaves at level 3). Ignoring underflow constraints and assuming maximum fan-out throughout, roughly how many leaf-level key entries can it index at most?

With maximum fan-out 4 at every internal level: level 1 (root) has up to 4 children, level 2 has up to 4×4=16 children (the leaves). Each of the 16 leaf nodes can hold up to 3 keys. Total ≈ 16 × 3 = 48 key entries at the leaf level in the best case.

Answer: Approximately 48 key entries (16 leaves × 3 keys each, at maximum fan-out)

Q4 A file is physically sorted by employee_id and has a primary index on employee_id with one entry per data block. Is this index sparse or dense, and why is this valid here specifically?

One entry per BLOCK (not per record) is exactly the definition of a sparse index. This is valid because the file is physically sorted by employee_id — given a target id, the index locates the correct block, and since records within that block are guaranteed to be in sorted order too, a short sequential scan within the block finds the exact record.

Answer: Sparse index — valid because the underlying file is sorted on the indexed field (employee_id)

Q5 Why does a plain B-Tree generally have LOWER fan-out than a B+-Tree built for the same block/node size?

A B-Tree's internal nodes must store both keys AND data pointers (since records can be referenced from any level, not just leaves), consuming more space per key and leaving room for fewer total keys/pointers within a fixed-size node. A B+-Tree's internal nodes store ONLY keys (all actual data references live exclusively in the leaves), so more keys fit per node of the same size — directly translating into higher fan-out and, consequently, fewer tree levels for the same number of total keys.

Answer: B-Tree internal nodes carry data pointers alongside keys, consuming space that reduces fan-out compared to B+-Tree's keys-only internal nodes

Weak entity PK

Owner's PK + weak entity's own discriminator/partial key. Requires an identifying relationship to the owner.

Superkey count formula

If a single attribute is the only candidate key among n total attributes, superkey count = 2^(n−1).

Primary key vs UNIQUE

Primary key: entity integrity forbids NULL outright. UNIQUE: only constrains non-NULL values to be distinct; how many NULLs it permits is DBMS/SQL-semantic dependent (most allow multiple). Never treat "UNIQUE = nullable primary key" as a universal rule.

Total vs partial participation

Total = double line, ER-level mandatory participation (commonly mapped to NOT NULL FK, but that's a mapping choice, not the definition). Partial = single line, optional. Put the FK on the total-participation side of a 1:1.

Division (÷)

R÷S = tuples t such that (t,s)∈R for EVERY s∈S. Classic "find X related to ALL of Y" query.

Relational completeness

RA ≡ safe TRC ≡ safe DRC in expressive power. "Safe" excludes expressions that could yield infinite results.

SQL logical evaluation order

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE can't use aggregates (runs before grouping); HAVING can.

NULL is three-valued

Comparisons with NULL → UNKNOWN, not TRUE/FALSE. NOT IN with a NULL in the list always returns zero rows.

X⁺ (attribute closure)

X is a candidate key iff X⁺ = all attributes of R AND no proper subset of X also satisfies this (minimality).

Normal form ladder

1NF: atomic values. 2NF: no partial dependency. 3NF: no transitive dependency (escape clause: RHS is prime). BCNF: every determinant is a superkey, no exceptions.

Lossless-join test

Decomposition of R into R1, R2 is lossless iff (R1∩R2)→R1 or (R1∩R2)→R2 holds in F⁺ (the closure of the FD set) — compute (R1∩R2)⁺, don't just eyeball the given FDs.

Conflict-serializability test

Build the precedence graph from RW/WR/WW conflicts across different transactions on the same item — serializable iff the graph is acyclic.

Recoverability classes

Strict ⊂ Cascadeless ⊂ Recoverable. Recoverable: reader commits after writer it read from. Cascadeless: no dirty reads at all. Strict: no read/overwrite until writer commits/aborts.

Strict 2PL

Holds write locks until commit — guarantees serializability AND prevents cascading rollback, unlike plain 2PL.

Timestamp ordering

Reject read if TS(Ti)<W-ts(Q); reject write if TS(Ti)<R-ts(Q) or <W-ts(Q) (Thomas Write Rule: ignore instead of rollback in the latter case). No deadlock, but more aborts than locking.

UNDO vs REDO

UNDO (before-image) = reverse uncommitted transactions' writes. REDO (after-image) = reapply committed transactions' writes. Deferred update needs REDO only; immediate update needs both.

Sparse index requires sorted file

Sparse = 1 entry/block, only valid when file is physically sorted on the indexed field → always primary/clustering, never secondary. Dense = 1 entry/record, works either way.

Primary index ≠ clustered index

Primary index = which KEY the index searches by. Clustered index = whether the DATA ROWS are physically stored in that key's order. They often coincide in textbook examples but aren't synonyms — a table has at most one clustered index but can have many secondary ones.

B+-Tree over B-Tree

Data pointers only in leaves → higher fan-out, fewer levels. Linked leaves → fast range scans. This is why DBMSs use B+-trees, not B-trees.

Practice — rapid-fire mix (original)

5 questions
Q1 R(A,B,C,D,E) has FDs A→B, BC→D, D→E. Is {A,C} a candidate key?

Compute {A,C}⁺: start {A,C}. A→B adds B: {A,B,C}. Now BC→D applies (both B,C present): add D: {A,B,C,D}. Now D→E applies: add E: {A,B,C,D,E} — all attributes covered. Check minimality: does {A}⁺ alone reach everything? A→B gives {A,B}, but BC→D needs C too, which isn't derivable from A alone — so {A} isn't sufficient. Similarly {C} alone derives nothing. So {A,C} is minimal.

Answer: Yes, {A,C} is a candidate key

Q2 True or false: every BCNF relation is also in 3NF.

True — BCNF is strictly stronger than (a subset of conditions compared to) 3NF; it removes 3NF's escape clause rather than adding a new requirement outside of it. Any relation satisfying the stricter BCNF condition automatically satisfies the looser 3NF condition too.

Answer: True

Q3 A schedule has only read operations from multiple transactions on shared data, no writes at all. Is it necessarily conflict-serializable?

Yes — conflicts only arise from RW, WR, or WW pairs; two reads (RR) never conflict, regardless of order. With no writes anywhere in the schedule, there are no conflicting operation pairs at all, so the precedence graph has no edges — trivially acyclic, and hence trivially conflict-serializable (equivalent to any serial order, including the schedule itself).

Answer: Yes — an all-read schedule has no conflicts at all, so it's trivially conflict-serializable

Q4 Which SQL clause would you use to filter groups based on their aggregate COUNT value, and why not WHERE?

HAVING is used, because it's evaluated after GROUP BY has formed the groups and aggregate values like COUNT are computed — WHERE runs before grouping even happens, so no aggregate value exists yet to filter on at that stage.

Answer: HAVING — because it runs after GROUP BY, when aggregates are actually available

Q5 A data file is NOT sorted by any particular field. Can it have a sparse index on any field?

No — sparse indexing fundamentally relies on physical file ordering matching the indexed field, so that one index entry per block is enough to locate the target via a short local scan. If the file has no sort order at all, no field can support a sparse index; only a dense index (one entry per record) would correctly locate every record.

Answer: No — an unsorted file cannot support a sparse index on any field; only dense indexing works
