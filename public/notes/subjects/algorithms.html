Asymptotic Analysis

BIG-O · BIG-Ω · BIG-Θ · LITTLE-o · RECURRENCES · MASTER THEOREM

Formal Definitions

Used to represent the time and space complexity of an algorithm as input size n → ∞.

  • O(g(n)) [Big-O, Upper Bound]: f(n) = O(g(n)) if ∃ c > 0, n₀ > 0 such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀.
  • Ω(g(n)) [Big-Omega, Lower Bound]: f(n) = Ω(g(n)) if ∃ c > 0, n₀ > 0 such that 0 ≤ c·g(n) ≤ f(n) for all n ≥ n₀.
  • Θ(g(n)) [Big-Theta, Tight Bound]: f(n) = Θ(g(n)) if f(n) = O(g(n)) and f(n) = Ω(g(n)). ∃ c₁, c₂ > 0, n₀ > 0 such that 0 ≤ c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀.
  • o(g(n)) [Little-o, Strict Upper Bound]: f(n) = o(g(n)) if ∀ c > 0, ∃ n₀ > 0 such that 0 ≤ f(n) < c·g(n) for all n ≥ n₀. Equivalently, lim(n→∞) f(n)/g(n) = 0.
  • ω(g(n)) [Little-omega, Strict Lower Bound]: f(n) = ω(g(n)) if ∀ c > 0, ∃ n₀ > 0 such that 0 ≤ c·g(n) < f(n) for all n ≥ n₀. Equivalently, lim(n→∞) f(n)/g(n) = ∞.

Common Growth Rates

In increasing order of complexity:

O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)

Properties

  • Transitivity: If f(n) = O(g(n)) and g(n) = O(h(n)), then f(n) = O(h(n)). Holds for Ω and Θ as well.
  • Sum Rule: O(f(n)) + O(g(n)) = O(max(f(n), g(n))). Drop lower-order terms.
  • Product Rule: O(f(n)) · O(g(n)) = O(f(n) · g(n)).

Recurrence Relations & Master Theorem

The Master Theorem solves recurrences of the form:

T(n) = aT(n/b) + f(n) where a ≥ 1, b > 1

Compare f(n) with n^(log_b(a)):

  • Case 1: f(n) = O(n^(log_b(a) - ε)) for ε > 0. → T(n) = Θ(n^(log_b(a)))
  • Case 2: f(n) = Θ(n^(log_b(a))). → T(n) = Θ(n^(log_b(a)) · log n)
  • Case 3: f(n) = Ω(n^(log_b(a) + ε)) for ε > 0, and a·f(n/b) ≤ c·f(n) for c < 1. → T(n) = Θ(f(n))

Substitution Method: Useful for T(n) = T(n-1) + 1 style recurrences (subtract and conquer).

GATE trap — where the standard Master Theorem does NOT apply

Confusing O (upper bound) with Θ (tight bound) is one common error — e.g. insertion sort is O(n²) and technically O(n³) too, but Θ(n²) is the tight worst-case bound. The bigger trap: the Master Theorem as stated above (three cases) only applies to recurrences of the exact form T(n) = aT(n/b) + f(n), with a single subproblem size, a ≥ 1, b > 1, and constant a and b. Don't reach for it blindly — check the shape first.

Do not apply blindly — recurrences that break the standard form
  • T(n) = T(n−1) + n (or any T(n−c) + f(n) pattern) — this is a "subtract and conquer" recurrence, not "divide and conquer" (no n/b term at all). Master Theorem doesn't apply; solve directly (this one gives Θ(n²), matching the Common Recurrences table above), typically via the substitution or iteration method.
  • T(n) = T(n/2) + T(n/3) + n — multiple subproblems of DIFFERENT relative sizes (unequal splitting). The standard Master Theorem assumes all a subproblems are the same size n/b; here they aren't, so it doesn't apply directly. Use the Akra–Bazzi method (a generalization) or recursion-tree analysis instead.
  • Irregular/unequal subproblem sizes in general — e.g. T(n) = T(n/3) + T(2n/3) + n. Same issue as above: no single b to compare against. Recursion-tree or Akra–Bazzi, not Master Theorem.
  • f(n) falling in a "gap" between cases — e.g. T(n) = 2T(n/2) + n/log n. Here f(n) = n/log n is asymptotically smaller than n = n^(log₂2) (ruling out Case 2) but not polynomially smaller by any ε > 0 (ruling out Case 1 too) — it falls in the gap between Case 1 and Case 2, where none of the three cases apply. These need the more general (Akra–Bazzi-style) extended master theorem or direct analysis.
  • T(n) = 2T(n/2) + n log n — another gap case, this time straddling Case 2 and Case 3: f(n) = n log n grows faster than n = n^(log₂2) (so it's not Case 2 as stated) but not polynomially faster by any fixed ε > 0, since log n grows slower than any nᵉ (so it's not Case 3 either). The basic three cases genuinely don't cover it — it needs the extended nᵏ log^p n form (giving Θ(n log² n) here) or a recursion-tree argument, not a direct plug-in to Case 2 or 3.
  • Non-polynomial f(n) with log/other factors that don't fit the nᵏ log^p n extended form also require care — verify the extended form's conditions before applying it, rather than assuming any log-containing f(n) automatically fits.

Amortized Analysis

Worst-case-per-operation analysis can be overly pessimistic for a sequence of operations where expensive operations are rare and "pay for themselves" across the sequence. The precise guarantee amortized analysis gives: for every sequence of m operations, the total cost is bounded by O(m × amortized cost per operation) — this is a worst-case bound on the total, holding for EVERY possible sequence, not a statement about typical or expected behavior. "Average cost per operation" is sometimes used as a shorthand for this, and it's mathematically fine as a description of what falls out of dividing total cost by m — but lead with the total-cost-bound framing above, because "average" too easily gets conflated with a different idea entirely:

Don't confuse amortized analysis with expected/average-case analysis

Amortized analysis is a deterministic, worst-case guarantee about a sequence of operations — no randomness or probability distribution over inputs is involved; the O(m × amortized cost) bound holds for the single worst possible sequence of m operations, guaranteed, every time. Expected/average-case analysis (e.g. quicksort's expected O(n log n)) is a probabilistic statement — it assumes a distribution over inputs (or over random choices the algorithm makes) and reasons about the mean outcome, which some particular run could still exceed. These are fundamentally different kinds of claims that happen to share the word "average" in casual descriptions — amortized cost is not a probabilistic average at all.

Canonical example — dynamic array (e.g. C++ vector, Java ArrayList) doubling

Appending to a dynamic array that doubles its capacity when full: a single append is usually O(1) (just place the element), but occasionally — when the array is full — it triggers a resize: allocate a new array of double the capacity and copy all existing elements over, an O(n) operation for that one append.

Individual (worst-case) cost of one append: O(n), when a resize happens to occur on that particular call. Amortized cost per append, across any sequence of n appends: O(1) — because resizes happen exponentially less often (at sizes 1, 2, 4, 8, ..., n) and each one only costs proportionally to the elements copied; summed across all n appends, the total work is O(n), so the average (amortized) per append is O(n)/n = O(1).

Three standard methods for amortized analysis
  • Aggregate method: compute the total worst-case cost T(n) of a sequence of n operations directly, then divide by n to get the amortized cost per operation. For dynamic array doubling: total cost of n appends = n (placements) + (1+2+4+...+n) (copying during resizes) ≤ n + 2n = O(n), so amortized cost = O(n)/n = O(1) per append.
  • Accounting (banker's) method: assign each operation an amortized cost that may be more than its actual cost; the surplus is saved as "credit" on specific data-structure elements, to be spent later by operations that cost more than their assigned amortized price. For dynamic array doubling: charge each append a flat amortized cost of O(1) — e.g. 3 units — using 1 unit for the placement itself and banking the other 2 as credit on that element, to later pay for it being copied (at most once) during a future resize.
  • Potential method: define a potential function Φ over the data structure's state (intuitively, "stored credit" as a function of the structure, not tied to individual elements) such that amortized cost = actual cost + ΔΦ (change in potential). For dynamic array doubling: a natural Φ = 2×(number of elements) − (current capacity) tracks exactly enough "banked" potential to pay for the next resize's copying cost when it occurs.

All three methods must agree on the final amortized bound for the same sequence of operations — they're different bookkeeping techniques for proving the same fact, and GATE questions typically only expect you to recognize the aggregate-method reasoning (as in the dynamic array derivation above), not carry out a full accounting/potential proof.

5 questions
Q1 Find the tight bound for T(n) = 3T(n/2) + n².

Here, a=3, b=2, f(n)=n². Compare f(n) with n^(log₂3) ≈ n^1.58. Since f(n) = Ω(n^(log₂3 + ε)) (Case 3), and 3(n/2)² = (3/4)n² ≤ cn² for c=3/4 < 1, the result is T(n) = Θ(f(n)).

Answer: Θ(n²)

Q2 Solve T(n) = 2T(n/2) + n log n.

Under the basic three-case formulation as many textbooks state it (Case 2 requiring f(n) = Θ(n^(log_b a)) exactly, with no log factor), this falls outside the stated cases: with a=2, b=2, f(n) = n log n compares against n^(log₂2) = n¹, and n log n is asymptotically larger than n but not polynomially larger by any fixed ε > 0 (log n grows slower than any nᵉ), so it doesn't cleanly satisfy Case 3's polynomial-gap requirement either. However, under the commonly used generalized Master Theorem for f(n) = n^k log^p n, this is exactly Case 2 with k=1, p=1: when f(n) = Θ(n^(log_b a) · log^p n) — i.e. a = b^k — the solution is T(n) = Θ(n^k · log^(p+1) n). Plugging in k=1, p=1 gives T(n) = Θ(n log² n).

Answer: Θ(n log² n) — falls outside the basic three-case Master Theorem, but is Case 2 of the generalized nᵏ log^p n version

Q3 True or False: 2^(n+1) = O(2ⁿ).

2^(n+1) = 2 · 2ⁿ. Since 2 · 2ⁿ ≤ c · 2ⁿ for c = 2, this statement is true.

Answer: True

Q4 True or False: 2^(2n) = O(2ⁿ).

2^(2n) = 4ⁿ. For 4ⁿ ≤ c · 2ⁿ, we need (4/2)ⁿ = 2ⁿ ≤ c, which is impossible for a constant c as n → ∞.

Answer: False

Q5 Consider T(n) = T(√n) + 1. Find the complexity.

Substitute n = 2^m, so m = log n. T(2^m) = T(2^(m/2)) + 1. Let S(m) = T(2^m). Then S(m) = S(m/2) + 1. By Master Theorem, S(m) = Θ(log m). Substituting back, T(n) = Θ(log log n).

Answer: Θ(log log n)

Searching

LINEAR SEARCH · BINARY SEARCH · TERNARY SEARCH · LOWER BOUNDS

Linear Search

Checks elements one by one. Works on unsorted arrays.

  • Best Case: O(1) (element found at index 0)
  • Worst/Average Case: O(n)

Binary Search

Requires a sorted array. Divides the search space in half each step.

mid = low + (high - low)/2

Using mid = (low + high)/2 can cause integer overflow in languages like C/C++/Java for large arrays. The formula above avoids this.

  • Best Case: O(1) (element is at mid)
  • Worst/Average Case: O(log n)

Variants: Finding the first or last occurrence of a duplicated element, finding the lower bound (first element ≥ x) or upper bound (first element > x).

Ternary Search

Divides the search space into three parts. Works on unimodal functions or sorted arrays. Complexity is O(log₃ n), which is asymptotically O(log n), but practically slower than binary search due to more comparisons per step.

Lower Bound for Comparison-based Search

A decision tree for searching an element in an array of size n has at least n+1 leaves (n successful outcomes + 1 unsuccessful). A binary tree with L leaves has height h ≥ ⌈log₂ L⌉. Thus, h ≥ log₂(n+1) = Ω(log n). Binary search achieves this lower bound and is optimal.

GATE trap

Off-by-one errors in binary search bounds: using while (low < high) vs while (low <= high), or updating low = mid instead of low = mid + 1 causing infinite loops. Binary search on answer technique is often tested in algorithmic questions (e.g., finding the minimum capacity of a ship to transport goods within D days).

Practice — GATE style (original)

5 questions
Q1 How many comparisons are required in the worst case to find an element in a sorted array of 1024 elements using binary search?

Convention: each iteration counts as one comparison — the equality test against the middle element (a "3-way" comparison: less / equal / greater) — and the count below is for the worst case (an unsuccessful search, or a successful search for the last element found). Worst-case comparisons = ⌈log₂(n+1)⌉ = ⌈log₂(1025)⌉ = 11. Or simply checking bounds: 1024 → 512 → 256 → 128 → 64 → 32 → 16 → 8 → 4 → 2 → 1 → 0.

Answer: 11 (under this counting convention). If GATE's own answer key uses a different comparison convention, the count can shift by one — when precision matters more than the exact number, it's safer to answer O(log n).

Q2 Given an array A of n distinct elements, we want to find both the minimum and maximum elements. What is the minimum number of comparisons needed?

Using tournament method (comparing pairs): ⌈3n/2 - 2⌉ comparisons. This is a standard well-known result for min-max finding.

Answer: ⌈3n/2 - 2⌉

Q3 What is the time complexity of searching in a sorted linked list?

Even though the list is sorted, random access is not possible — finding the midpoint itself requires traversal from a known point, costing O(n) just to locate it. Binary search can still be performed conceptually (halving the search range each step), but each halving pays an O(n) traversal cost to find that step's midpoint, so the total running time is O(n) overall — it provides no asymptotic advantage over linear search on a linked list, even though the underlying procedure (repeatedly comparing against a midpoint and discarding half the range) is not literally the same algorithm as linear search.

Answer: O(n)

Q4 Binary search is performed on the sorted array: [2, 4, 6, 8, 10, 12, 14, 16]. If the target is 6, what is the sequence of mid elements examined? (assume mid = floor((low+high)/2) and 0-based indexing)

low=0, high=7. mid=3 (val 8). 6 < 8, so high=2. low=0, high=2. mid=1 (val 4). 6 > 4, so low=2. low=2, high=2. mid=2 (val 6). Found.

Answer: 8, 4, 6

Q5 An array contains n elements. A linear search is performed to find an element. If the element has a uniform probability of being anywhere in the array, what is the average number of comparisons?

Assumes the element is guaranteed to be present in the array (search-key presence probability p=1) — this is the standard GATE assumption unless stated otherwise; if p<1, the average also has to account for the probability of an unsuccessful full-array scan, changing the formula. The element can be at index 1, 2, ..., n. Average = (1 + 2 + ... + n) / n = [n(n+1)/2] / n = (n+1)/2.

Answer: (n+1)/2

Sorting

COMPARISON SORTS · NON-COMPARISON SORTS · STABILITY · LOWER BOUND Ω(n log n)

Comparison-Based Sorts

  • Bubble Sort: Repeatedly swaps adjacent elements. O(n²) worst/avg. Can be optimized to O(n) best case (with a swapped flag). Stable. In-place.
  • Selection Sort: Finds the minimum and swaps it to the front. O(n²) in all cases. Not stable (e.g., [4a, 4b, 2] → [2, 4b, 4a]). In-place.
  • Insertion Sort: Builds the sorted array one element at a time. O(n²) worst/avg. O(n) best case (when nearly sorted). Stable. In-place. Excellent for small n.
  • Merge Sort: Divide & conquer. Divides array in half, recursively sorts, and merges. Θ(n log n) in all cases. Stable. NOT in-place (requires O(n) extra space).
  • Quick Sort: Divide & conquer. Picks a pivot, partitions array around it. O(n log n) average. O(n²) worst case (when array is already sorted and bad pivot like first/last element is chosen). Randomization gives expected O(n log n) running time under the standard model (by making the bad-pivot pattern independent of input order) — the worst case still remains O(n²); randomization doesn't eliminate the worst case, it just makes it astronomically unlikely for any fixed input. GATE can and does ask for the worst-case behavior explicitly, so never state randomized quicksort's worst case as O(n log n). Not stable. In-place.
  • Heap Sort: Builds a max-heap, repeatedly extracts max. Θ(n log n) all cases. Not stable. In-place.

Non-Comparison Sorts

  • Counting Sort: O(n + k) time and space, where k is the range of inputs. Works well when k = O(n). Stable.
  • Radix Sort: O(d(n + k)) time, where d is the number of digits. Sorts digit by digit using a stable sort (like Counting Sort).
  • Bucket Sort: Expected O(n) time under suitable input-distribution assumptions — specifically that elements are drawn roughly uniformly over a known range, so they spread evenly across buckets (roughly O(1) elements per bucket, keeping per-bucket sorting cheap) and the number of buckets scales with n. This is not a universal average case: with a skewed distribution or too few buckets, elements can pile into one bucket, and sorting that bucket with a comparison sort degrades the total to O(n²) worst case. Distributes elements into buckets, then sorts each bucket (often with insertion sort). Useful for uniformly distributed floats in [0, 1).
Lower Bound Proof Sketch: Ω(n log n)

A sorting algorithm based on comparisons can be modeled as a decision tree. For n elements, there are n! possible permutations (leaves of the tree). A binary tree of height h has at most 2^h leaves. Thus, 2^h ≥ n! ⇒ h ≥ log₂(n!). Using Stirling's approximation, log₂(n!) = Θ(n log n). Hence, the worst-case number of comparisons is Ω(n log n).

GATE trap

1. Quicksort's worst-case time is O(n²), not O(n log n) — it happens when the partition is always highly unbalanced (e.g., sorted array with first/last element pivot).
2. Merge sort requires O(n) extra space, making it unfavorable for large in-memory arrays compared to Quicksort.
3. Stability matters when sorting multi-key records (e.g., sort by name, then by age). Stable sorts preserve the relative order of equal keys.

Practice — GATE style (original)

5 questions
Q1 Which sorting algorithm is optimal for an array that is almost sorted (few inversions)?

Insertion sort runs in O(n + I) time where I is the number of inversions. For an almost sorted array, I is very small, making insertion sort run in O(n) time.

Answer: Insertion Sort

Q2 You need to sort a very large dataset that cannot fit into RAM. Which sorting algorithm is best?

External Merge Sort is used for data that is too large to fit in memory (external memory). It sorts chunks in RAM, writes them to disk, and then merges them.

Answer: External Merge Sort

Q3 What is the worst-case time complexity of Quick Sort, and what input causes it (assuming the pivot is the first element)?

Worst-case is O(n²). It occurs when the array is already sorted (ascending or descending), leading to partitions of size 0 and n-1 at every step.

Answer: O(n²) for an already sorted array

Q4 A sorting algorithm is stable if...

It maintains the relative order of records with equal keys. If A appears before B in the input and A = B in value, A will appear before B in the sorted output.

Answer: Relative order of equal elements is preserved

Q5 How many comparisons does Selection Sort make on an array of size n?

Selection sort always makes (n-1) + (n-2) + ... + 1 = n(n-1)/2 comparisons, regardless of the initial order of elements.

Answer: n(n-1)/2 (which is Θ(n²))

Hashing

HASH FUNCTIONS · COLLISION HANDLING · CHAINING · OPEN ADDRESSING · LOAD FACTOR

Hash Functions

A hash function maps a key to an index in the range [0, m−1]. The ideal hash function provides a uniform distribution of keys across all slots.

  • Division method: h(k) = k mod m (choose m as prime, not power of 2)
  • Multiplication method: h(k) = ⌊m(kA mod 1)⌋ where 0 < A < 1

Collision Handling

  • Separate chaining: each slot is a linked list. Average case (uniform hashing assumption): search/insert/delete O(1 + α) where α = n/m (load factor). Worst case: O(n) — if every key hashes to the same slot, that slot's list holds all n elements and must be traversed linearly. GATE options frequently mix these two, so state which one is being asked for.
  • Open addressing: probe sequence within table. Expected number of probes depends heavily on both the load factor α and the probing scheme used (linear probing clusters and degrades faster as α grows; double hashing stays closer to the ideal uniform-hashing bound) — there's no single formula independent of which scheme is in use, only the general expected-probes approximations below. Worst case for any open-addressing scheme is still O(n) probes (table nearly full, long probe chain before an empty slot is found).
    • Linear probing: h(k,i) = (h(k) + i) mod m — suffers from primary clustering
    • Quadratic probing: h(k,i) = (h(k) + c₁i + c₂i²) mod m — secondary clustering
    • Double hashing: h(k,i) = (h₁(k) + i·h₂(k)) mod m — best distribution
Load factor (α)
α = n / m

For chaining α can exceed 1; for open addressing α < 1 (table must have empty slots).

Expected probes
Chaining successful ≈ 1 + α/2 Chaining unsuccessful ≈ 1 + α

Under the standard uniform-hashing approximation (each probe sequence treated as equally likely to be any permutation of the table — the idealized model that double hashing comes closest to matching in practice), open addressing gives:

Open addressing unsuccessful ≈ 1/(1−α) Open addressing successful ≈ (1/α)·ln(1/(1−α))

These two formulas are not universal — they hold under the uniform-hashing idealization, not for every probing scheme exactly as implemented. Linear probing is the standard counterexample: because of primary clustering, its real expected probe counts run noticeably worse than these idealized formulas predict, especially as α approaches 1 — GATE sometimes expects you to know linear probing underperforms this bound, not match it exactly.

Practice — GATE style (original)

5 questions
Q1 Given a hash table of size 10 and hash function h(k) = k mod 10, insert 15, 25, 35 using linear probing. How many probes are required for 35?

Insert 15: h(15)=5 (1 probe). Insert 25: h(25)=5 (collision), probe to 6 (2 probes). Insert 35: h(35)=5 (collision), probe to 6 (collision), probe to 7 (3 probes).

Answer: 3 probes

Q2 In a hash table using chaining, the load factor is α. What is the expected time for an unsuccessful search?

In chaining, an unsuccessful search must traverse the entire linked list at the hashed slot. The average length of this list is exactly α. Computing the hash function takes O(1) time.

Answer: O(1 + α)

Q3 Which collision resolution technique is most prone to primary clustering?

Linear probing sequentially checks slots, causing contiguous blocks of occupied slots to merge, which is known as primary clustering. Quadratic probing causes secondary clustering. Double hashing avoids both.

Answer: Linear probing

Q4 A hash table of size m=11 uses double hashing with h₁(k) = k mod 11 and h₂(k) = 1 + (k mod 10). Insert key 33. What is the probe sequence?

h₁(33) = 33 mod 11 = 0. If slot 0 is full, we use h₂(33) = 1 + (33 mod 10) = 1 + 3 = 4. The probe sequence is (h₁(k) + i·h₂(k)) mod 11. For i=0, index is 0. For i=1, index is (0 + 1·4) = 4. For i=2, index is (0 + 2·4) mod 11 = 8.

Answer: 0, 4, 8, 1, 5, ...

Q5 Can the load factor α be greater than 1 in open addressing?

No. In open addressing, every element is stored directly in the hash table array, so the number of elements (n) cannot exceed the number of slots (m) — α = n/m can reach at most 1 in principle. But α = 1 means the table is completely full: there is no empty slot left for the next insertion's probe sequence to terminate on, so a functioning open-addressing table (one that can still insert) needs at least one empty slot at all times. That's why the usable/conventional range for open addressing is α < 1, strictly — matching the table above, not "≤ 1."

Answer: No — and in practice α must be strictly less than 1 (α < 1) for the table to remain usable

Divide & Conquer

DIVIDE · CONQUER · COMBINE · RECURRENCES · CLASSIC ALGORITHMS

The D&C Paradigm

Split problem into subproblems, solve recursively, combine solutions. Divide and conquer works well when a problem can be decomposed into smaller, sufficiently independent subproblems whose solutions can be recursively combined — independence/separability plus a combine step is the defining property, not "optimal substructure" (that's primarily a dynamic-programming/optimization concept — see the D&C vs DP comparison later in this page for why the two shouldn't be conflated).

Master Theorem quick reference

For recurrences of the form T(n) = aT(n/b) + Θ(nᵏ logᵖ n), compare a with bᵏ:

If a > bᵏ ⟹ T(n) = Θ(n^(log_b a)) If a = bᵏ ⟹ T(n) = Θ(nᵏ log^(p+1) n) (if p ≥ 0) If a < bᵏ ⟹ T(n) = Θ(nᵏ logᵖ n)

These clean, exact Θ conclusions require f(n) itself to be pinned down by a matching Θ(nᵏ logᵖ n) bound. An upper bound alone — f(n) = O(nᵏ logᵖ n), without a matching lower bound — is not sufficient to derive a tight Θ result for T(n): a looser O-only bound can leave real gaps where none of the three cases (or even the extended form) cleanly applies, and you'd need recursion-tree analysis or the more general Akra–Bazzi method instead.

Comparison: D&C vs DP

Divide & Conquer breaks a problem into independent smaller subproblems and combines their solutions. Optimal substructure is NOT a defining requirement of D&C — merge sort is the textbook example: its two halves share no overlap, and there's no "optimal choice" being made anywhere in the algorithm, yet it's still canonical D&C.

Dynamic Programming specifically exploits overlapping subproblems together with an appropriate optimal-substructure/recurrence relationship — that overlap (and the resulting redundant recomputation) is exactly what memoization/tabulation is built to eliminate. 0/1 Knapsack is the classic example: subproblems on smaller capacities/item-sets recur repeatedly across different branches of the recursion.

Don't collapse this into "both rely on optimal substructure" — overlapping subproblems is the property that actually distinguishes DP from D&C. Optimal substructure alone is necessary but not sufficient to make something DP; plenty of D&C algorithms (e.g. finding the max of an array via D&C) have optimal substructure too, without ever becoming DP.

GATE trap

Quicksort worst case happens when array is already sorted and we pick the first/last element as pivot. Strassen's constant is large, which means naive matrix multiplication is faster for small n (the crossover point).

Q1 Solve the recurrence T(n) = 2T(n/2) + n/log n.

Greedy Algorithms

GREEDY CHOICE · OPTIMAL SUBSTRUCTURE · CLASSIC PROBLEMS · GREEDY vs DP

Greedy Paradigm

Make locally optimal choice at each step, hoping for global optimum. Two properties needed:

  • Greedy choice property
  • Optimal substructure

Classic greedy algorithms

  • Activity/Job selection: sort by finish time, select non-overlapping — O(n log n)
  • Fractional knapsack: sort by value/weight ratio, fill greedily — O(n log n). NOTE: 0/1 knapsack is NOT greedy (it's DP)
  • Huffman coding: build optimal prefix-free code tree by repeatedly merging the two lowest-frequency nodes — standard min-heap implementation: O(n log n); if the input frequencies are already sorted, a two-queue linear-time construction achieves O(n) instead (no heap needed — one queue holds the original sorted leaves, the other holds newly-merged internal nodes, and the next-smallest of the two front elements is always cheaply available)
    • How it works: repeatedly merge two lowest-frequency nodes
    • Properties: no codeword is a prefix of another; optimal for variable-length encoding
  • Job sequencing with deadlines: sort by profit, assign latest available slot
  • Minimum number of platforms/intervals problem: track arrivals/departures, sort all times, and count max overlaps
When greedy fails

0/1 knapsack, shortest path with negative weights (Dijkstra fails), coin change (for arbitrary denominations).

"Top-down" and "bottom-up" describe DP's two computation styles, not Greedy

Don't equate Greedy with "top-down" — that's a mismatch of vocabulary. "Top-down" and "bottom-up" are the two ways to compute a DP solution: top-down starts from the original problem and recurses into subproblems, caching results (memoization); bottom-up starts from the smallest subproblems and iteratively builds up to the final answer (tabulation). Both compute the same recurrence and typically have the same asymptotic complexity. Greedy, in contrast, isn't doing either — it makes one irrevocable choice per step and never revisits or re-solves anything, so it doesn't fit the top-down/bottom-up framing at all.

Optimal substructure alone doesn't guarantee a correct DP solution

The problem having optimal substructure is necessary but not sufficient — a DP solution is only actually correct if all of the following hold together: the state is defined precisely enough to capture every distinction that affects the answer, the recurrence/transition correctly combines subproblem solutions into the current one, and the base cases are correct. A DP built on a real optimal-substructure problem can still give a wrong answer if the state is under-specified (missing information needed to make future decisions correctly) or the recurrence misses a case — "optimal substructure holds" describes the problem, not a guarantee about any particular DP formulation of it.

Why the same greedy rule works for one and not the other

Fractional knapsack's greedy choice (always take as much as possible of the highest ratio item) is provably optimal because any leftover capacity can always be filled with a fraction of the next-best item — nothing is ever wasted. 0/1 knapsack breaks this: once an item must be taken whole, a high-ratio item that doesn't fit exactly can leave capacity that no other item fills as efficiently, so a locally greedy pick can lock out a better overall combination — this is exactly why 0/1 needs DP's exhaustive-but-structured search over combinations instead.

Dynamic Programming

OPTIMAL SUBSTRUCTURE · OVERLAPPING SUBPROBLEMS · MEMOIZATION · TABULATION

Dynamic Programming Paradigm

DP solves problems by combining the solutions to overlapping subproblems. It stores the results of subproblems (memoization or tabulation) to avoid redundant recomputation, bringing exponential time complexities down to polynomial.

Two key properties required for DP:

  • Optimal Substructure: An optimal solution to the problem contains optimal solutions to its subproblems.
  • Overlapping Subproblems: The space of subproblems is small; the recursive algorithm visits the same subproblems repeatedly.
These two properties are independent — a problem needs both to make DP the useful technique

Optimal substructure is about how the problem's optimal solution decomposes; overlapping subproblems is about how many distinct subproblems that decomposition actually generates. A problem can have optimal substructure without overlapping subproblems — merge sort is the textbook example: the optimal (sorted) result of an array is built from the optimally-sorted results of its two halves (optimal substructure holds), but the recursive calls on the left half and right half are on completely disjoint index ranges, so no subproblem is ever solved twice. There's nothing to memoize, and applying DP machinery (a table, memoization) would add overhead for no benefit — plain divide & conquer is already the right tool. DP is worth using specifically when both properties hold together: optimal substructure justifies combining subproblem solutions correctly, and overlapping subproblems is what makes caching those solutions actually save work.

Top-down (Memoization) vs Bottom-up (Tabulation): Both generally have the same asymptotic time complexity. Top-down is easier to write (recursion + cache) and only computes needed states. Bottom-up has no recursion overhead and is often easier to space-optimize.

Classic DP Problems

0/1 Knapsack: Items cannot be split. DP[i][w] is the maximum value using first i items and weight limit w.

DP[i][w] = max(DP[i-1][w], val[i] + DP[i-1][w-wt[i]])

Time: O(nW). Space: 2D table = O(nW); since each row depends only on the row directly above it, this optimizes down to a 1D array = O(W), reused across items.

GATE trap — iterate capacity BACKWARD in the 1D optimization

When collapsing the 2D table to a 1D array, the capacity loop must run from W down to wt[i] (backward), not from 0 up to W. Updating forward would let an item's own just-updated value feed into a LATER (higher-capacity) update within that same item's pass — effectively letting that item be picked more than once, which silently turns 0/1 Knapsack into Unbounded Knapsack. Iterating backward guarantees every value read on the right-hand side still belongs to the previous item's row, preserving the "each item used at most once" constraint. This single implementation detail is one of the most common 0/1 Knapsack bugs and a frequent GATE trace-the-code question.

Longest Common Subsequence (LCS): Length of the longest subsequence common to both strings X and Y.

DP[i][j] = DP[i-1][j-1] + 1 if X[i] = Y[j] DP[i][j] = max(DP[i-1][j], DP[i][j-1]) if X[i] ≠ Y[j]

Time: O(mn), Space: O(mn) (can be optimized to O(min(m,n))).

Longest Increasing Subsequence (LIS): Naive DP takes O(n²), optimizing to O(n log n) with patience sorting/binary search.

Matrix Chain Multiplication (MCM): Minimum scalar multiplications to compute product of n matrices. Dimensions p[0]...p[n].

DP[i][j] = min_{i≤k<j} (DP[i][k] + DP[k+1][j] + p[i-1]p[k]p[j])

Time: O(n³), Space: O(n²).

Edit Distance: Minimum operations (insert, delete, replace) to convert string X to Y.

DP[i][j] = min(insert, delete, replace) DP[i][j] = min(DP[i][j-1]+1, DP[i-1][j]+1, DP[i-1][j-1] + cost)

Time: O(mn), Space: O(mn).

DP vs Naive Recursion

Example: Fibonacci numbers. Naive recursion F(n) = F(n-1) + F(n-2) takes exponential time O(2ⁿ). DP (memoization or tabulation) stores previously computed values, reducing time to linear O(n) and making it practically computable.

GATE trap

DP ≠ Recursion. A problem must have overlapping subproblems to benefit from DP (e.g., Divide & Conquer problems like merge sort have independent subproblems, so DP doesn't apply). Also, 0/1 Knapsack time is pseudo-polynomial O(nW), not strictly polynomial. Always check if a greedy approach works first (it's simpler and takes less space).

Q1 To compute the LCS of two strings of lengths m and n, how many entries does the conventional DP table have, including the base-case row/column for empty prefixes?

Q2 Can the 0/1 Knapsack DP table be space-optimized to a 1D array, and why must the capacity loop go backward?

Yes. The recurrence DP[i][w] only depends on row i−1, so a 1D array of size W+1, reused across items, is enough — reducing space from the 2D table's O(nW) down to O(W).

The capacity loop must iterate backward (from W down to wt[i]) for correctness, not just style: updating forward would let an item's own already-updated (current-row) value leak into a later, higher-capacity update within the same item's pass — which effectively lets that single item be selected more than once, turning 0/1 Knapsack into Unbounded Knapsack by accident. Going backward guarantees every value read on the right-hand side still belongs to the previous item's row.

Answer: Yes, space reduces to O(W) — but only if the capacity loop runs backward; forward iteration silently breaks the 0/1 (each-item-once) constraint

Q3 Is the O(nW) time complexity of the 0/1 Knapsack problem considered polynomial?

No, it is pseudo-polynomial. The number of bits needed to represent the capacity W is log₂W. Therefore, W is exponential with respect to its input size (log₂W), making O(nW) an exponential time algorithm in the worst case.

Answer: No, it is pseudo-polynomial

Q4 Which classic DP problem uses a recurrence relation that checks all possible splitting points k between i and j?

Matrix Chain Multiplication (MCM) iterates through every possible split point k (where i ≤ k < j) to find the minimum cost to multiply matrices from index i to j.

Answer: Matrix Chain Multiplication

Q5 How can we identify whether a problem should be solved with DP instead of Greedy?

DP is especially appropriate when the problem has optimal substructure and subproblems overlap substantially, allowing memoization/tabulation to reuse computed results and avoid repeated work — that combination is the primary practical criterion, not just about greedy "failing." (Overlapping subproblems isn't a strict mathematical requirement for applying memoization — you technically could memoize even with little or no overlap — but without substantial overlap there's nothing to save, so DP wouldn't offer its usual asymptotic advantage over plain recursion/D&C.) Within the optimal-substructure class, greedy is worth considering only when a greedy-choice property can additionally be proven (an optimal solution can always be built by making the locally best choice at each step). But the failure of a greedy strategy alone doesn't automatically point to DP — plenty of problems without a greedy-choice property are instead solved with divide and conquer, graph algorithms, backtracking, branch-and-bound, flow algorithms, or other techniques. DP specifically fits when that failure is paired with the optimal-substructure + overlapping-subproblems combination described above (e.g. 0/1 Knapsack).

Answer: When the problem has optimal-substructure + substantially overlapping subproblems — a failed greedy strategy alone doesn't imply DP is the right tool; other techniques (D&C, backtracking, branch-and-bound, etc.) may fit instead

Graph Algorithms

BFS/DFS · TOPOLOGICAL SORT · MST · SHORTEST PATHS · COMPLEXITY

Traversals and Topological Sort

BFS (Queue): Shortest path in unweighted graphs. DFS (Stack/Recursion): Cycle detection, connectivity, and topological sorting. Both take O(V+E) time using an adjacency list.

Topological Sort: A linear ordering of vertices in a Directed Acyclic Graph (DAG) such that for every directed edge u→v, u comes before v. Used in task scheduling and prerequisite ordering.

GATE trap — topological ordering exists IFF the graph is a DAG

A topological ordering exists if and only if the directed graph is acyclic. If the graph has even one directed cycle, no valid linear ordering can satisfy "u before v for every edge u→v" — some vertex in the cycle would have to come both before and after another vertex in the same cycle, a contradiction. Conversely, every DAG has at least one valid topological order (often more than one, when the DAG has "parallel" unrelated branches).

Also don't forget the graph must be directed in the first place: an undirected graph has no conventional topological ordering at all — the notion of "u before v along edge u→v" presupposes edges have a direction; an undirected edge {u,v} gives no such constraint to order by.

  • DFS-based topological sort: run DFS from every unvisited vertex; when a vertex FINISHES (all its descendants have been fully explored), push it onto a stack. Popping the stack at the end gives the topological order — equivalently, this is a reverse post-order traversal. Detects a cycle for free: if DFS ever encounters a "back edge" (an edge to a vertex still on the current recursion stack, i.e. an ancestor), the graph has a cycle and no topological order exists.
  • Kahn's Algorithm (BFS-based): repeatedly find and remove a vertex with in-degree 0 (place it in the output, and decrement the in-degree of its neighbors), using a queue to track vertices whose in-degree has just dropped to 0. If the algorithm terminates having output fewer than V vertices, the remaining vertices form a cycle — this is Kahn's built-in way to detect a non-DAG, distinct from DFS's back-edge check.
GATE trap — a DAG can have MULTIPLE valid topological orders

Don't assume "the" topological order is unique — most DAGs admit several valid linear orderings, and GATE frequently asks you to count them or list all of them. Kahn's algorithm gives a direct, mechanical way to read off whether multiple orders exist, right from the trace itself:

  • If, at some step, more than one vertex simultaneously has in-degree 0, you have a genuine choice of which to output next — this branching means multiple valid topological orders exist (one for each possible choice at that step, and at every subsequent step where the same thing happens).
  • Conversely, if at every step exactly one vertex has in-degree 0 (no ties, ever), there was never a choice to make — the topological order is unique.

This also gives a fast way to count total topological orders for small DAGs: multiply together the number of available choices at each step where a choice existed (though for graphs with more complex structure, the choices at different steps aren't always independent, so this simple product can overcount — full enumeration or careful counting is needed in general).

Minimum Spanning Tree (MST)

MST properties, stated precisely (tie cases matter — this is a classic GATE trap): the Cut Property says a lightest edge crossing any cut belongs to some MST — not necessarily every MST, unless that lightest edge is the unique minimum for that cut, in which case it belongs to every MST. The Cycle Property says a strictly heaviest edge on any cycle cannot belong to any MST — but if there are ties for maximum weight on that cycle, a maximum-weight edge may still belong to some MST (just not all of them, and not together with another tied max edge on the same cycle unless removing it doesn't disconnect anything relevant). For a connected graph, the MST is unique overall if all edge weights in the graph are distinct (a disconnected graph has no single MST to begin with — only a minimum spanning forest).

GATE trap

Don't read "min edge crossing a cut belongs to the MST" as "the MST" (definite article, implying uniqueness) when weights can tie — with ties, multiple different MSTs can exist and a given lightest-crossing edge is only guaranteed to be in at least one of them. The property becomes a uniqueness guarantee only when the minimum (or maximum, for the cycle property) is strict/unique.

O((V+E) log V) assumes an adjacency list + binary heap (each edge relaxation triggers an O(log V) heap update). Dijkstra & Bellman-Ford

Dijkstra uses a greedy min-heap approach, and its correctness guarantee requires all edge weights to be non-negative. Bellman-Ford relaxes all edges V−1 times. If a V-th relaxation succeeds, it detects a negative weight cycle reachable from the source (cycles the source can't reach go undetected).

Floyd-Warshall

Uses DP on intermediate vertices: dist[i][j] = min(dist[i][j], dist[i][k] + dist[k][j]). Handles negative weights; a negative value on the diagonal (D[i][i] < 0) after completion signals a negative cycle through vertex i — see the caveat below on what that means for the rest of the matrix.

GATE trap — why a negative cycle actually matters, not just "detect and stop"

Don't memorize "Bellman-Ford detects negative cycles" as an isolated fact — understand what breaks. If a source-reachable negative-weight cycle exists, you can loop around it indefinitely, making the total path weight to any vertex reachable FROM that cycle arbitrarily small (trending toward −∞). In other words, for every vertex reachable from a source-reachable negative cycle, shortest-path distance is not a well-defined finite minimum at all — there's no smallest value, only an unbounded downward sequence. This is exactly why Bellman-Ford's extra Vth pass exists: it isn't just a diagnostic flag, it's catching a case where the entire premise of "shortest path distance" breaks down for the affected vertices.

GATE trap — after Floyd-Warshall finds D[i][i] < 0, not every entry stays meaningful

A negative value on the diagonal (D[i][i] < 0 for some i) correctly signals that vertex i lies on a negative-weight cycle. But don't assume every OTHER entry D[p][q] in the completed matrix is still a valid, meaningful shortest-path distance — any pair (p,q) whose shortest path is affected by (passes through, or can be re-routed through) that negative cycle no longer has a well-defined finite shortest distance either, for the same reason as Bellman-Ford: you could route through the cycle repeatedly to make that path arbitrarily small. Only pairs entirely unaffected by any negative cycle retain their computed D[p][q] as a genuine shortest-path value — treat the whole matrix as suspect once any diagonal entry is negative, not just that one row/column.

Both optimizations matter, and the complexity is different without them:

  • Path compression only (no union by rank): amortized O(log n) per operation.
  • Union by rank/size only (no path compression): O(log n) per operation.
  • Neither optimization (naive linked-list-style union-find): a chain can degrade to O(n) per find operation in the worst case.

GATE's "nearly O(1)" framing for Kruskal's specifically assumes the optimized version (path compression + union by rank) — if a question describes an unoptimized Union-Find implementation, don't default to O(α(n)); use the appropriate weaker bound above.

5 questions
Q1 Which data structure is essential for efficiently implementing Kruskal's algorithm?

Kruskal's algorithm needs to rapidly check if adding an edge forms a cycle. A Disjoint Set (Union-Find) data structure does this efficiently — with path compression and union by rank/size, in amortized O(α(n)) time (near-constant, not exactly O(1)).

Answer: Union-Find (Disjoint Set)

Q2 In Bellman-Ford, how many passes of edge relaxation are required to detect a negative weight cycle reachable from the source?

The shortest path can have at most V−1 edges. The algorithm normally does V−1 passes. A V-th pass is done strictly to detect negative cycles: if any distance can still be relaxed on this extra pass, a negative-weight cycle reachable from the source exists. This "reachable from the source" qualifier matters — Bellman-Ford only relaxes edges along paths from the source, so a negative cycle sitting in a part of the graph the source can't reach (a disconnected component, or a component only reachable INTO, not FROM, the cycle) will never trigger a relaxation on the V-th pass and goes undetected by this run.

Answer: V passes in total (V−1 normal passes + 1 detection pass), and this detects only source-reachable negative cycles

Q3 True or False: Topological sorting can be performed on any directed graph.

False. Topological sort is only defined for Directed Acyclic Graphs (DAGs). If a graph contains a cycle, no valid linear ordering is possible.

Answer: False (only for DAGs)

Q4 For a connected undirected weighted graph, if all edge weights are distinct, how many Minimum Spanning Trees can it have?

A standard property of MSTs is that for a connected graph, if all edge weights are distinct, the MST is absolutely unique. The "connected" condition matters: an MST is only defined for a connected graph in the first place — a disconnected graph has no single spanning tree at all, only a minimum spanning forest (one MST per connected component), and the uniqueness argument applies separately within each component.

Answer: Exactly one (for a connected graph)

Q5 Why is Dijkstra's algorithm not guaranteed to be correct on graphs with negative edge weights?

Dijkstra's is a greedy algorithm. Once a vertex is extracted from the min-heap, its shortest path is considered "finalized" and never revisited. A negative edge could offer a cheaper path to an already-finalized vertex later, which Dijkstra's ignores by construction. Note the precise phrasing: this is a correctness guarantee, not a claim that Dijkstra necessarily produces a wrong answer on every graph with a negative edge — on some specific negative-edge graphs (and orderings) the greedy choices happen to still land on the correct distances by luck. Dijkstra's proof of correctness assumes non-negative weights, so it's unsafe to rely on whenever a negative edge is present, whether or not a particular instance happens to come out right.

Answer: Because the algorithm's correctness proof depends on extracted vertices being truly finalized, an assumption that non-negative weights guarantee and negative weights can violate

Asymptotic Notations

O(g): Upper bound. Ω(g): Lower bound. Θ(g): Tight bound. Master theorem: compare f(n) with n^(log_b(a)) across 3 cases.

Searching & Lower Bounds

Binary Search: O(log n). Any comparison-based sorting algorithm has worst-case lower bound Ω(n log n) — not every execution of every run; e.g. insertion sort takes O(n) on already-sorted input. Lower bound to search an unsorted array: Ω(n).

Sorting Algorithm Limits

Merge: Θ(n log n) stable, out-of-place. Quick: worst O(n²), avg O(n log n), in-place. Heap: O(n log n) in-place, unstable.

Hashing Basics

Load factor α = n/m. Chaining: average O(1 + α), worst case O(n). Under the standard uniform-hashing approximation, open addressing's expected probes for unsuccessful search ≈ 1/(1−α) — this is idealized (real behavior depends on probing scheme too, e.g. linear probing runs worse); worst case O(n) regardless.

Divide & Conquer

Recurrence patterns. Merge sort: T(n) = 2T(n/2) + O(n). Binary search: T(n) = T(n/2) + O(1). Strassen's Matrix Mult: O(n^2.81).

Greedy Algorithms

Activity Selection (sort finish time), Huffman Coding (min heap), Fractional Knapsack (sort val/wt). All operate in O(n log n) in general — Huffman drops to O(n) with a two-queue approach if frequencies are already sorted.

Dynamic Programming

0/1 Knapsack: time O(nW); space O(nW) as 2D, optimized to O(W) as 1D — but only with the capacity loop iterated backward. LCS O(mn), LIS O(n log n), MCM O(n³). DP requires optimal substructure AND overlapping subproblems.

Graph: Spanning Trees

Kruskal (sort edges + Union-Find) O(E log E). Prim (Heap) O(E log V). Adding constant weight to all edges preserves the MST.

Graph: Shortest Paths

Dijkstra O((V+E)log V), fails on negative edges. Bellman-Ford O(VE), detects source-reachable negative cycles — affected vertices have no well-defined finite shortest distance. Floyd-Warshall O(V³), all-pairs DP; D[i][i]<0 signals a negative cycle, which taints other affected entries too, not just the diagonal.

Key Distinctions

Greedy vs DP: Greedy has no look-ahead. D&C vs DP: D&C has independent subproblems, DP has overlapping subproblems.

5 questions
Q1 What is the worst-case time complexity of Quick Sort?

For standard comparison-based Quick Sort, the worst-case complexity is Θ(n²) — this is a property of the algorithm in general, independent of any particular pivot-selection strategy or input.

A concrete example that causes this worst case: if the pivot is consistently the smallest or largest element of the (sub)array being partitioned — e.g. always picking the first or last element as pivot on an already-sorted array — each partition step only shrinks the problem by 1, giving the recurrence T(n) = T(n−1) + O(n), which solves to Θ(n²). This is one example that triggers the worst case, not a definition of what the worst-case complexity is.

Answer: Θ(n²) (worst case), e.g. triggered by always picking the smallest/largest element as pivot

Q2 True or False: Adding a constant weight to all edges in a graph preserves the shortest paths.

False. Paths with more edges will accumulate more of the added weight, potentially changing which path is considered the shortest overall.

Answer: False

Q3 What is the maximum number of edges in an n-node acyclic undirected graph?

An acyclic undirected graph is a tree (if connected) or a forest. A tree with n nodes has exactly n−1 edges.

Answer: n − 1

Q4 Does Dijkstra's algorithm work for graphs with cycles?

Yes, Dijkstra's algorithm handles cycles perfectly well, provided that there are no negative weight edges in the graph.

Answer: Yes, as long as there are no negative weights

Q5 Which data structure is used to implement Huffman coding in the general case, and what's the time complexity? Can it be improved?

Huffman coding repeatedly extracts the two minimum-frequency nodes to combine them. A Min-Heap supports each extraction in O(log n), giving O(n log n) overall — this is the standard, general-case answer, since arbitrary input frequencies aren't sorted. If the input frequencies are already sorted, a two-queue approach (no heap) can find the next two minimums in O(1) each, bringing total construction down to O(n).

Answer: Min-Heap, O(n log n) in general; O(n) with two queues if frequencies are already sorted
