Introduction & Lexical Analysis

COMPILER PHASES · TOKENS & LEXEMES · REGEX → NFA → DFA

The phases of a compiler

PhaseInput → OutputTypical technique
Lexical analysissource chars → tokensDFA / regex
Syntax analysistokens → parse treeCFG / LL, LR parsing
Semantic analysisparse tree → annotated treetype checking, scope resolution
Intermediate code genannotated tree → IR (3AC)SDT
Code optimizationIR → optimized IRdata-flow analysis
Code generationIR → target coderegister allocation
Front end / middle end / back end

Lexical + syntax + semantic analysis + IR generation = front end (depends only on the source language, machine-independent). Code generation = back end (machine-dependent: instruction selection, register allocation, target-specific scheduling). Optimization doesn't fit cleanly into either — most textbooks place machine-independent optimization (constant folding, dead-code elimination, common-subexpression elimination on the IR) in a conceptual middle end between the two, reserving "back end" for machine-dependent optimizations (peephole optimization, instruction scheduling) plus code generation itself. For GATE you don't need to insist on a strict three-way split, but don't flatly call optimization "back end" — say which kind of optimization (machine-independent vs machine-dependent) you mean.

Tokens, lexemes, and patterns

  • Token — a category, e.g. ID, NUM, KEYWORD.
  • Lexeme — the actual substring matched, e.g. count, 42.
  • Pattern — the rule (regex) describing what lexemes a token can match.
GATE trap

The lexical analyzer resolves ambiguity between keywords and identifiers using the maximal munch (longest match) rule, and ties between rules matching the same longest length are broken by rule priority (order listed) — e.g. if matches both the keyword rule and the identifier rule; keyword wins because it's listed first, not because of length.

Regex → NFA → DFA pipeline

A lexer generator (like lex/flex) compiles the set of token regexes into a single NFA (Thompson's construction), converts it to a DFA (subset construction), and minimizes that DFA — the same automata-theory pipeline from Theory of Computation, applied to build a real scanner.

regex --Thompson's construction--> NFA NFA --subset construction--> DFA DFA --Hopcroft/Moore minimization--> minimal DFA
NFA→DFA state explosion

Subset construction can blow up an n-state NFA to as many as 2ⁿ DFA states in the worst case — GATE frequently asks you to actually perform the construction on a small NFA and count resulting DFA states.

Error recovery in lexical analysis

Common panic-mode strategies: delete one character and resume, insert a missing character, or skip to the next delimiter (whitespace). Lexical errors are relatively rare because almost any character sequence can form some valid lexeme (e.g. as an identifier).

Practice — GATE style (original)

5 questions
Q1 Which phase of the compiler is responsible for detecting that a variable was used without being declared?

Undeclared-variable use is a scope/binding issue, not a grammatical (syntax) one — the sequence of tokens can be perfectly well-formed. This is checked during semantic analysis, which builds and consults the symbol table.

Answer: Semantic analysis

Q2 Given the input ifx = 5; (no space between "if" and "x"), what token(s) does the lexer produce for the first word, and why?

The maximal-munch rule makes the lexer greedily consume the longest possible match. "ifx" as a whole matches the identifier pattern (letters), and it's longer than just "if", so the lexer produces one ID token "ifx" — it does NOT split it into keyword "if" + identifier "x".

Answer: A single identifier token "ifx" (maximal munch overrides the keyword match)

Q3 An NFA for a certain regex has 5 states. What is the maximum number of states in the DFA produced by subset construction, before minimization?

Subset construction builds one DFA state per distinct reachable subset of the NFA's state set — worst case, all 2⁵ subsets are reachable and distinct.

Answer: 2⁵ = 32 states (worst case, before minimization)

Q4 Classify the compiler phases into front end and back end, and explain why this split is useful for building compilers for multiple source languages and target machines.

Front end (lexical, syntax, semantic analysis, IR generation) is primarily source-language dependent; back end (code generation, plus machine-dependent optimization) is primarily target-machine dependent. In practice this is an idealization — real compilers can have target-dependent semantic constraints, ABI considerations, target-specific IR decisions, and other source-target interactions that blur the boundary somewhat. IR generation itself is commonly classed as part of the front end, but some compiler architectures place parts of IR construction/transformation in the middle end instead — treat this as a terminology convention rather than a fixed rule. Machine-independent optimization sits on the IR between the two and is often called the middle end. Because front and back ends communicate through a shared, largely machine-independent IR, you can mix-and-match — reuse one front end with several back ends (multiple targets) or one back end with several front ends (multiple source languages) instead of writing a full compiler for every language×machine pair.

Answer: Front end = language-dependent (lexical/syntax/semantic/IR-gen); back end = machine-dependent (codegen, machine-dependent optimization); machine-independent optimization sits between them (middle end); the IR boundary lets front/back ends be mixed and reused

Q5 A lexer encounters the character sequence @ which matches no token pattern in the language. What is a typical panic-mode recovery action?

Typical recovery: delete/skip the offending character and resume scanning from the next one, reporting an error. Note that lexical errors aren't limited to stray illegal characters like this — they also include cases such as unterminated string literals, malformed numeric literals, invalid escape sequences, and unterminated comments, each of which may call for a different recovery heuristic (e.g. scanning to the next quote/newline/delimiter).

Answer: Skip/delete the bad character and resume scanning, reporting an error

Top-Down Parsing

CFG RECAP · LEFT RECURSION & FACTORING · FIRST/FOLLOW · LL(1) PARSING TABLE

Why left recursion breaks top-down parsing

A top-down parser expands the leftmost nonterminal first. With A → Aα | β, trying to expand A immediately calls A again before consuming any input — infinite recursion with no progress.

Standard left-recursion elimination
A → Aα | β transforms to: A → βA' A' → αA' | ε

Left factoring

When two productions for the same nonterminal share a common prefix, the parser can't decide which to pick by looking only one token ahead. Left-factor to defer the decision.

A → αβ₁ | αβ₂ transforms to: A → αA' A' → β₁ | β₂

FIRST and FOLLOW sets

SetMeaning
FIRST(α)terminals that can begin a string derived from α (includes ε if α can derive ε)
FOLLOW(A)terminals that can immediately follow A in some derivation from the start symbol (includes $ if A can be the last symbol)
GATE trap — FOLLOW never truly "contains ε"

FOLLOW sets never include ε itself as a symbol — when a production's right side can derive ε, that ε-possibility propagates into computing OTHER symbols' FOLLOW sets, but ε is never listed as a member of any FOLLOW set. Only FIRST sets can list ε as a member.

Building the LL(1) parsing table

For each production A → α: add it to table cell M[A, a] for every terminal a in FIRST(α); if ε ∈ FIRST(α), also add it to M[A, b] for every b in FOLLOW(A).

Grammar is LL(1) iff...

No cell of the table ever gets two different productions filled in — equivalently, for every nonterminal with multiple productions, their FIRST sets must be pairwise disjoint, and at most one alternative can derive ε (and if one does, its FIRST and the other alternatives' FOLLOW must not overlap).

Ambiguous and left-recursive grammars are never LL(1)

Left recursion always creates a table conflict (infinite expansion attempts for the same lookahead). Ambiguous grammars have some string with two parse trees, which manifests as two productions competing for the same table cell.

Practice — GATE style (original)

5 questions
Q1 Eliminate left recursion from: E → E + T | T.

Matching the pattern A→Aα|β with α="+T", β="T": rewrite as E→TE', E'→+TE'|ε — the standard transformation moves the recursive part to the right via a new nonterminal E'.

Answer: E → T E' , E' → + T E' | ε

Q2 For the grammar S→aS|aSbS|ε (a genuinely ambiguous grammar for a classic language), why does LL(1) table construction necessarily fail?

Both productions S→aS and S→aSbS begin with terminal "a", so FIRST of both alternatives overlaps at "a" — the LL(1) table cell M[S,a] would need to hold both productions simultaneously, which is disallowed. Left-factoring itself is a purely mechanical step (factor out the common "a" prefix) and can always be applied here; the deeper problem is that this grammar is ambiguous (some strings, like "aab", have 2 distinct parse trees), and no LL(1) grammar can be ambiguous. So even after factoring out the common prefix, the resulting grammar still can't be made LL(1) — the ambiguity would have to be removed by rewriting the grammar's structure (not just factoring prefixes) before an LL(1) table could exist for it.

Answer: FIRST sets of the two S-productions both contain "a" → table conflict; ambiguous grammars can never be LL(1)

Q3 Given FIRST(A)={a,b,ε} and FOLLOW(S)={c,d,$}, for the production S→A, which table cells get filled for this production?

The rule for a production X→α always looks at FOLLOW of the LHS nonterminal X, not of anything on the right-hand side — here the production is S→A, so the LHS is S and it's FOLLOW(S) that matters (FOLLOW(A) is irrelevant to filling row S). For every terminal in FIRST(A) except ε, add S→A at that column: M[S,a] and M[S,b]. Since ε∈FIRST(A), also add S→A at every column in FOLLOW(S): M[S,c], M[S,d], M[S,$].

Answer: M[S,a], M[S,b], M[S,c], M[S,d], M[S,$] — five cells total

Q4 Left-factor the grammar: Stmt → if E then Stmt else Stmt | if E then Stmt.

Both alternatives share the prefix "if E then Stmt". Factor it out into a new nonterminal covering just the differing tail (else-branch or nothing): Stmt → if E then Stmt Stmt', Stmt' → else Stmt | ε.

Answer: Stmt → if E then Stmt Stmt' , Stmt' → else Stmt | ε

Q5 Does every regular language have an equivalent LL(1) grammar? (Note: this is different from asking whether every grammar someone writes for a regular language is automatically LL(1) — it usually isn't, e.g. S→Sa|a for a⁺ is left-recursive and not LL(1) as written.)

Yes. Since regular languages are a strict subset of deterministic context-free languages, an equivalent unambiguous, non-left-recursive grammar can always be constructed for one (typically via a right-linear form derived from its DFA), and such a grammar is LL(1). This is a claim about the language's inherent parsability, not about any one arbitrary grammar someone happens to write for it — a specific grammar for a regular language can still be ambiguous or left-recursive as given, making that particular grammar not LL(1), even though an LL(1)-equivalent grammar for the same language exists.

Answer: Yes — every regular language has an equivalent LL(1) grammar, even though an arbitrarily-written grammar for it need not itself be LL(1).

Bottom-Up Parsing (LR family)

SHIFT-REDUCE · LR(0) ITEMS & HANDLES · SLR / CLR / LALR · CONFLICTS

Shift-reduce parsing basics

A bottom-up parser maintains a stack and repeatedly either shifts the next input symbol onto the stack, or reduces a string on top of the stack (a "handle") back to a nonterminal using a production, right-to-left, building the parse tree from leaves to root — the reverse of top-down parsing.

Power hierarchy of the LR family

LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ CLR(1) / LR(1)
ParserLookahead sourceTable sizePower
LR(0)none — reduce on any inputsmallestweakest
SLR(1)FOLLOW(A) of the reduced nonterminalsmallweak — approximates lookahead
LALR(1)merged, item-specific lookaheadssame size as SLRstrong — used by yacc/bison
CLR(1) / LR(1)full, item-specific lookaheadslargest (many more states)strongest
GATE trap — LALR merging can introduce reduce-reduce conflicts

LALR(1) is built by merging CLR(1) states with identical cores (same LR(0) items, different lookaheads). This merge can never introduce a NEW shift-reduce conflict that wasn't already latent, but it CAN introduce a new reduce-reduce conflict that didn't exist in the full CLR(1) table — a classic GATE distinction question.

Shift-reduce vs reduce-reduce conflicts

Shift-reduce conflict

Parser can't decide whether to shift the next token or reduce what's on the stack. Classic example: dangling-else grammar. Default resolution (as in yacc) is usually to shift.

Reduce-reduce conflict

Two different productions could both validly reduce the same handle — the grammar is ambiguous with respect to that construct, or the parser class is too weak to disambiguate it (common with LALR on certain grammars, absent in CLR for the same grammar).

Augmented grammar and LR(0) items

Add a new start production S' → S so the parser has a unique accept state. An LR(0) item is a production with a dot marking how much of the RHS has been recognized so far, e.g. A → α·β.

Closure and Goto operations

closure(I): if A→α·Bβ is in I, add all items B→·γ for every production of B. goto(I, X): the closure of all items A→αX·β where A→α·Xβ was in I — this builds the transition to the next state on symbol X.

Handle-pruning intuition

A handle is a substring on the stack matching some production's RHS, such that reducing it is a step in the reverse of some rightmost derivation. Bottom-up parsing = repeatedly find and reduce the handle ("handle pruning") until only the start symbol remains.

Practice — GATE style (original)

5 questions
Q1 Rank LR(0), SLR(1), LALR(1), and CLR(1) from weakest to strongest in terms of the class of grammars each can parse without conflict.

Each adds lookahead precision over the last: LR(0) uses none, SLR(1) approximates with a static FOLLOW set, LALR(1) uses item-specific (but merged) lookaheads, and CLR(1) uses full unmerged item-specific lookaheads.

Answer: LR(0) < SLR(1) < LALR(1) < CLR(1)

Q2 A grammar's CLR(1) parsing table has no conflicts, but its LALR(1) table (built by merging same-core CLR states) does have a conflict. What kind of conflict must it be, and why?

It must be a reduce-reduce conflict. Merging states with the same core can combine two different lookahead sets on the same reduce item, causing two productions to become eligible to reduce on an overlapping lookahead that wasn't shared before merging. Merging is proven to never introduce a fresh shift-reduce conflict, since shift actions depend only on the core (which is identical before/after merging), not on the lookaheads.

Answer: A reduce-reduce conflict — merging can create these but never a new shift-reduce conflict

Q3 Compute closure({S'→·S}) given the augmented grammar S'→S, S→AA, A→aA|b.

Start with S'→·S. Since the dot precedes nonterminal S, add all S-productions with dot at the start: S→·AA. Since the dot in that new item precedes nonterminal A, add all A-productions with dot at start: A→·aA and A→·b. No further nonterminals appear right after a dot, so closure is complete.

Answer: { S'→·S, S→·AA, A→·aA, A→·b }

Q4 Why does the "dangling else" grammar cause a shift-reduce conflict in LR parsing, and what is the conventional default resolution?

When the parser has just reduced/recognized "if E then Stmt" and sees "else" as the next token, it can either shift the else (attaching it to the nearer if) or reduce the current Stmt (attaching else, if it comes later, to an outer if) — both are grammatically valid continuations, creating a shift-reduce conflict. The conventional default (used by yacc/bison) is to prefer shift, which correctly implements the standard "else binds to the nearest unmatched if" rule.

Answer: Shift-reduce conflict; default resolution is to shift, which matches else to the nearest if

Q5 A CLR(1) parser for a certain grammar has 20 states; the LALR(1) parser for the same grammar has 12 states. Explain why LALR always has fewer or equal states compared to CLR for the same grammar.

LALR(1) is constructed by taking the CLR(1) automaton and merging every group of states that share the identical LR(0) core (same items ignoring lookaheads) into a single state, only keeping the union of their lookaheads. Since merging can only combine states together and never split them, the resulting state count can only decrease or stay the same, never increase.

Answer: LALR merges same-core CLR states into one, so it can only have fewer or equal states, never more

Syntax-Directed Translation & Intermediate Code

SYNTHESIZED VS INHERITED · S-ATTRIBUTED & L-ATTRIBUTED · THREE-ADDRESS CODE

Synthesized vs inherited attributes

Synthesized attribute

Computed from a node's children (bottom-up flow). E.g. an expression's type computed from its subexpressions' types.

Inherited attribute

Computed from a node's parent or siblings (top-down/left-to-right flow). E.g. passing the declared type down to each identifier in a declaration list.

S-attributed vs L-attributed definitions

ClassRuleCompatible with
S-attributedonly synthesized attributesbottom-up (LR) parsing
L-attributedsynthesized + inherited, but each inherited attribute depends only on attributes to its left (siblings before it, or the parent)top-down (LL) parsing, and bottom-up with care
GATE trap

Every S-attributed definition is automatically L-attributed (a stricter subset), but not vice versa. GATE often gives an SDD and asks "is this S-attributed, L-attributed, both, or neither" — check whether ANY inherited attributes exist first; if none, it's S-attributed (hence also L-attributed). If inherited attributes exist, verify they only look leftward.

Three-address code (3AC)

An intermediate representation where each instruction has at most one operator and three addresses (2 operands + 1 result), making it close to assembly but still machine-independent.

Expression: x = (a + b) * (c - d) 3AC: t1 = a + b t2 = c - d t3 = t1 * t2 x = t3
Common 3AC representations

Quadruples: (op, arg1, arg2, result) — 4 fields. Triples: (op, arg1, arg2) where arg1/arg2 can reference another triple's position instead of a temp name — no separate result field, saving space but complicating code motion (reordering breaks position-based references).

Syntax trees vs DAGs for expressions

A syntax tree has one node per subexpression occurrence. A DAG (directed acyclic graph) shares nodes for common subexpressions — (a+b)*(a+b) as a DAG has just ONE node for a+b, used twice, enabling common-subexpression elimination for free during IR construction.

Backpatching for control flow

For boolean expressions and control statements, target jump addresses are often unknown when the jump instruction is generated (e.g. the "then" branch hasn't been code-generated yet). Backpatching leaves the jump target blank initially and fills it in once the target address becomes known.

Practice — GATE style (original)

5 questions
Q1 An SDD has the rule E.val = E1.val + T.val where E, E1, T are all on the production's right-hand or left-hand side appropriately (E→E1+T). Is E.val synthesized or inherited?

E.val is being computed for the LHS nonterminal E using only attribute values from its children (E1 and T) on the RHS — the defining characteristic of a synthesized attribute (bottom-up information flow).

Answer: Synthesized

Q2 An SDD contains only synthesized attributes throughout. Classify it as S-attributed, L-attributed, both, or neither.

S-attributed is defined as having ONLY synthesized attributes. Since S-attributed is always a subset of L-attributed (the leftward-dependency condition on inherited attributes is vacuously satisfied when there are none), this SDD qualifies as both.

Answer: Both S-attributed and L-attributed

Q3 Generate three-address code for x = a * b + c * d.

Break the expression into elementary operations, introducing one temp per operator, evaluating left-to-right respecting precedence (* before +).

Answer: t1 = a * b; t2 = c * d; t3 = t1 + t2; x = t3

Q4 Why can triples be problematic when a code optimizer wants to reorder or delete instructions, compared to quadruples?

A triple's operands can reference another triple by its position/index in the instruction list rather than by a named temporary. If the optimizer reorders, inserts, or deletes instructions, every position-based reference throughout the list can silently become wrong, requiring careful renumbering. Quadruples avoid this because they refer to results via explicitly named temporaries, which remain valid regardless of instruction order.

Answer: Triples use position-based references that break under reordering; quadruples use named temporaries that don't

Q5 Draw the key difference (conceptually) between a syntax tree and a DAG for the expression (a+b)*(a+b), and state one optimization this difference enables.

A syntax tree would have two completely separate subtrees for the two occurrences of "a+b", each with its own '+' node and leaf nodes for a and b. A DAG instead has a single '+' node for "a+b", with both "uses" of it (as left and right operand of '*') pointing to that same shared node — the identical subexpression is stored and computed once.

Answer: The DAG shares the single "a+b" node instead of duplicating it, directly enabling common-subexpression elimination

Runtime Environments & Symbol Tables

ACTIVATION RECORDS · STATIC VS DYNAMIC SCOPING · STORAGE ALLOCATION STRATEGIES

Storage allocation strategies

StrategyWhereUsed for
Static allocationfixed address, compile-timeglobals, static locals — no recursion support
Stack allocationruntime stack, LIFOlocal variables, parameters — supports recursion
Heap allocationruntime heap, arbitrary lifetimedynamically sized/lifetime data (malloc-style)
GATE trap — why static allocation can't support recursion

Static allocation gives each variable exactly ONE fixed memory address for the entire program run. A recursive function needs a fresh, independent copy of its locals for every active call — impossible with a single fixed address, since the second call would overwrite the first's still-in-use values. This is precisely why recursive languages require stack (or heap) allocation for locals.

Activation record layout

┌────────────────────┐ ↑ higher addresses │ actual parameters │ ├────────────────────┤ │ return address │ ├────────────────────┤ │ control link (dyn.) │ → points to caller's AR ├────────────────────┤ │ access link (static) │ → points to lexically enclosing AR ├────────────────────┤ │ saved machine state │ ├────────────────────┤ │ local variables │ ├────────────────────┤ │ temporaries │ └────────────────────┘ ↓ lower addresses (typical stack growth)
Control link vs access link

Control link (dynamic link) points to the caller's AR — used to restore the caller's frame on return, tracks the actual call sequence. Access link (static link) points to the AR of the lexically (textually) enclosing scope — used to resolve non-local variable references in nested-function languages. These two links coincide only when a function is called from directly within its own lexical parent.

Static vs dynamic scoping

Static (lexical) scoping

A name resolves to the binding visible in the enclosing source-code block at the point where it's written — determined entirely at compile time. Used by nearly all modern languages including C.

Dynamic scoping

A name resolves to the most recent binding still active on the call stack at runtime — depends on the call sequence, not the source layout. Rare in modern languages (older Lisp, some shell variables).

Symbol table

A compiler-wide data structure mapping identifier names to their attributes: type, scope, memory location/offset, size. Implemented typically as a hash table for O(1) average lookup, often organized as nested scopes (a stack of tables, one per active block) to support shadowing.

Practice — GATE style (original)

5 questions
Q1 Why can't a language that supports recursive functions use pure static (fixed-address) allocation for local variables?

Static allocation binds each variable to one fixed memory address for the program's entire lifetime. A recursive call creates a new logical instance of the same local variable while the outer call's instance is still active and needed — with only one address available, the inner call would overwrite the outer call's value, corrupting it. Stack allocation solves this by giving each call its own activation record with independent storage.

Answer: Recursion needs multiple simultaneous live instances of the same local variable, which one fixed address cannot provide

Q2 Function A (defined at the top level) calls function B, which is nested inside function C. Function A itself is not inside C. Under static scoping with access links, does B's access link point to A's activation record?

No. The access link (static link) always points to the AR of the lexically enclosing scope in the SOURCE CODE — B is lexically nested inside C, so B's access link points to C's activation record, regardless of who actually called B at runtime. Only the control (dynamic) link would point to A's activation record in this scenario, since A is the actual caller.

Answer: No — B's access link points to C's AR (lexical parent), not A's; A's AR is reachable only via the control link

Q3 Under dynamic scoping, consider: global x=1; function f(){print(x);} function g(){int x=2; f();} Calling g() — what does f print?

Dynamic scoping resolves a name using the most recent binding still active on the call stack at the moment of use, not the textual/lexical structure. When f() executes print(x), the most recently active binding of x on the call stack is g's local x=2 (g called f, and g's x is still in scope on the stack), so that's what resolves.

Answer: 2 (under dynamic scoping — it would print 1 under static/lexical scoping, since f is lexically outside g)

Q4 What is stored for each identifier entry in a compiler's symbol table, and why is a hash table the typical underlying structure?

Typical fields: name, type, scope/block level, storage location or stack offset, and size. A hash table is preferred because identifier lookup happens extremely frequently throughout compilation (every reference to every variable), and hashing gives average O(1) insert/lookup, which is essential for compiling large programs efficiently.

Answer: Name, type, scope, memory offset, size; hash table chosen for average O(1) lookup given how frequently it's queried

Q5 A function has 3 parameters, 2 local variables, and makes one nested call. At the moment that nested call's activation record is pushed, how many activation records exist on the stack in total for this call chain (assuming this was the initial/outermost call)?

The outermost function's own AR was already on the stack when it was called, and it remains on the stack (not popped) while it waits for the nested call to return. Pushing the nested call's AR adds one more on top — so both are simultaneously present.

Answer: 2 activation records (the outer call's AR remains on the stack beneath the newly pushed nested call's AR)

Code Optimization

BASIC BLOCKS & CFG · LOCAL VS GLOBAL OPTIMIZATION · LOOP OPTIMIZATION · DATA-FLOW ANALYSIS

Basic blocks and control-flow graphs

A basic block is a maximal sequence of instructions with a single entry (first instruction) and single exit (last instruction) — control enters only at the top and leaves only at the bottom, with no branches into or out of the middle. A control-flow graph (CFG) has basic blocks as nodes and possible control transfers as edges.

Identifying leaders (basic block starts)

A leader is: (1) the first instruction, (2) any instruction that is the target of a jump/branch, or (3) any instruction immediately following a jump/branch. Each basic block runs from one leader up to (but not including) the next leader.

Local vs global optimization

Local optimization

Analyzed within a single basic block only. Examples: local common-subexpression elimination, constant folding, dead-code elimination within the block. Simple, no data-flow analysis needed.

Global optimization

Analyzed across the whole CFG (multiple blocks). Needs data-flow analysis (reaching definitions, live variables) since a variable's value may come from different blocks depending on the execution path taken.

Common optimizations

OptimizationWhat it does
Constant foldingevaluate constant expressions at compile time: x=2+3 → x=5

Loop-invariant code motionhoist computations that don't change across iterations out of the loop

Data-flow analyses — the three the GATE 2027 syllabus names

The official GATE 2027 Compiler Design syllabus explicitly lists three data-flow analyses: constant propagation, liveness analysis, and common subexpression elimination. All three sit inside the same general iterative data-flow framework — a CFG, per-block IN/OUT information, transfer functions, and a meet operator combining information at join points, iterated to a fixed point — but their actual data-flow domains, transfer functions, and meet operators differ, so don't treat them as one interchangeable GEN/KILL recipe. Concretely: liveness is a set-based backward analysis, reaching definitions and common-subexpression/available-expressions analysis are set-based forward analyses (all three do reduce to GEN/KILL-style set equations), while constant propagation is a lattice/value analysis — its "state" per variable is a three-level lattice value (⊤ / constant / ⊥), not a set of definitions or expressions, and its meet operator combines lattice values rather than unioning or intersecting sets of statements.

Reaching definitions (forward analysis)

A definition of variable x reaches a point p if there's a path from the definition to p along which x is not redefined. Direction: forward. Meet operator: union (∪) — a definition reaches if it comes along any path. Used to detect use of possibly-uninitialized variables and as the foundation for constant propagation.

OUT[B] = GEN[B] ∪ (IN[B] − KILL[B])    IN[B] = ∪ OUT[predecessors of B]
Live variable analysis (backward analysis)

A variable x is live at point p if there's a path from p to some use of x along which x is not redefined first. Direction: backward (computed from uses back toward definitions). Meet operator: union (∪). Used for register allocation and dead-code/dead-store elimination.

IN[B] = USE[B] ∪ (OUT[B] − DEF[B])    OUT[B] = ∪ IN[successors of B]

Constant propagation

Constant propagation replaces variables with their known constant values at compile time. If every reaching definition of variable x assigns the same constant value c, then every subsequent use of x can be replaced by c. This often enables further optimizations like constant folding (x=5; y=x+3 → y=8) and dead-code elimination.

Constant propagation — lattice model

Each variable's state at any program point is one of three values on a lattice:

⊤ (top/undefined) — variable not yet assigned on any reaching path
c (constant) — variable has the same constant value c on all reaching paths
⊥ (bottom/NAC) — variable has different values on different paths (Not A Constant)

The lattice order is: ⊤ > any constant c > ⊥. The meet operator (∩) combines values at join points:

c ∩ c = c  |  c₁ ∩ c₂ = ⊥ (if c₁ ≠ c₂)  |  c ∩ ⊤ = c  |  c ∩ ⊥ = ⊥
Transfer function for constant propagation

For each statement x = expr in a basic block:

• If expr is a constant c → set x = c
• If expr involves only variables with known constant values → evaluate and set x = result (constant folding)
• If any variable in expr is ⊥ (NAC) → set x = ⊥
• If any variable in expr is ⊤ (undefined) → set x = ⊤

At join points (where multiple CFG paths merge), use the meet (∩) operator — this is intersection, not union. A variable is constant only if ALL incoming paths agree on the same value.

Worked example — constant propagation on a CFG

Consider three basic blocks with edges B1→B2, B1→B3, B2→B4, B3→B4:

B1: x = 5; y = 3
B2: y = 7  (only reached if condition true)
B3: y = 7  (only reached if condition false)
B4: z = x + y

At B4's entry (join of B2 and B3): x = 5 from both paths → x is constant 5. y = 7 from B2, y = 7 from B3 → y is constant 7 (both agree). Therefore z = 5 + 7 = 12 — all three variables are constants at B4.

But if B3 had y = 9 instead, then at B4: y = 7 ∩ 9 = ⊥ (NAC) — y cannot be propagated, and z = ⊥.

GATE trap — constant propagation

⚠️ At join points, constant propagation uses intersection (meet/∩), not union. A variable is constant only if ALL paths agree on the same value. This is the opposite of reaching definitions (which uses union — a definition reaches if it comes from ANY path). Confusing meet vs join operators is the #1 trap in GATE data-flow questions.

Common subexpression elimination (CSE)

CSE identifies expressions that are computed more than once with the same operand values, and replaces redundant recomputations with a stored result. An expression a op b is an available expression at point p if every path from the entry to p evaluates a op b, and neither a nor b is redefined after the last such evaluation.

Available expressions analysis (for CSE)

Direction: forward. Meet operator: intersection (∩) — an expression is available only if it's available on ALL incoming paths.

OUT[B] = e_GEN[B] ∪ (IN[B] − e_KILL[B])    IN[B] = ∩ OUT[predecessors of B]

e_GEN[B]: expressions computed in B whose operands are not subsequently redefined in B.
e_KILL[B]: all expressions involving any variable defined in B.

CSE worked example

Before CSE: t1 = a + b; c = t1 * d; ... t2 = a + b; e = t2 * f;

After CSE: t1 = a + b; c = t1 * d; ... e = t1 * f; (reuse t1, eliminate redundant a+b)

CSE requires that neither a nor b was redefined between the two occurrences of a + b.

Loop optimization — the highest-value target

Loops execute far more often than straight-line code, so optimizing them gives disproportionate speedup. Key targets: identify natural loops (via dominators/back edges in the CFG), hoist loop-invariant computations, and eliminate redundant induction variables.

Practice — GATE style (original)

8 questions
Q1 Given the 3AC sequence: (1) t1=a+b (2) if t1>0 goto (5) (3) t2=a-b (4) goto (6) (5) t2=a*b (6) print t2 — identify the leaders.

Leader rule: instruction 1 (first instruction) is always a leader. Instruction 5 is a leader (target of the goto in line 2). Instruction 3 is a leader (immediately follows the branch at line 2). Instruction 6 is a leader (target of goto at line 4, and also immediately follows instruction 5's fallthrough... but since line 6 is a jump target it qualifies either way).

Answer: Leaders at instructions 1, 3, 5, 6

Q2 Is dead-code elimination within a single basic block a local or global optimization, and why?

Determining whether a value computed within one basic block is ever used again purely within that same block requires only examining that block's own instruction sequence — no information about other blocks or possible execution paths is needed. This makes it a local optimization by definition (confined to a single basic block's analysis).

Answer: Local optimization — it only needs information within the single block

Q3 Which classical data-flow analysis is computed in the backward direction, and what is it used for?

Live variable analysis is computed backward — starting from a variable's use and propagating "liveness" back toward its definitions, since whether x is live at a point depends on whether it's used somewhere later along some future path. It's primarily used for register allocation (a dead register can be reused) and dead-store elimination.

Answer: Live variable analysis — used for register allocation and dead-store elimination

Q4 Rewrite this loop after applying loop-invariant code motion: for(i=0;i<n;i++){ x = a*b; sum += x + i; }

The computation x = a*b doesn't depend on the loop variable i and produces the same result on every iteration — it's loop-invariant and can be safely hoisted out to execute exactly once, before the loop begins, instead of n times inside it.

Answer: x = a*b; for(i=0;i<n;i++){ sum += x + i; }

Q5 Explain the difference in direction between reaching-definitions analysis and live-variable analysis, and why they must go in opposite directions.

Reaching definitions asks "which earlier definition might still be the current value at this point?" — a question that's naturally answered by propagating information forward from definitions toward later uses. Live variables asks "will this value be used somewhere later?" — a question naturally answered by propagating information backward from uses toward earlier points. The two questions are inherently mirror images (looking forward from a write vs. looking forward to a future read from the current point), which is exactly why one is a forward data-flow problem and the other a backward one.

Answer: Reaching definitions is forward (definition → later point); live variables is backward (point → later use) — they answer mirror-image questions

Q6 In the CFG below, can x be constant-propagated at point P? B1: x=5. B2: x=5. B3 (joins B1,B2): use x at point P.

At the join point (entry of B3), we apply the meet operator to the values of x from both incoming paths. From B1: x = 5. From B2: x = 5. Meet: 5 ∩ 5 = 5 — both paths agree on the same constant value. Therefore x can be replaced by 5 at point P.

Answer: Yes — x = 5 on both incoming paths, so meet gives constant 5

Q7 B1: a=3, b=4. B2: a=3, b=7. B3 (joins B1,B2): c = a + b. After constant propagation, what is c at B3?

At B3 entry: a = 3 ∩ 3 = 3 (constant). b = 4 ∩ 7 = ⊥ (NAC — different values on different paths). Since b is NAC, the expression a + b cannot be fully evaluated. c = ⊥ (not a constant). Only a can be propagated: c = 3 + b.

Answer: c is NAC (⊥) — a can be propagated as 3, but b differs across paths so c = 3 + b

Q8 Given: t1 = a*b; c = t1 + d; a = 7; t2 = a*b; e = t2 + d. Can CSE eliminate the second computation of a*b?

Between the first a*b (t1) and the second a*b (t2), the variable a is redefined (a = 7). This means the expression a*b is killed — the second a*b uses a different value of a than the first. The expression is NOT available at the second computation point, so CSE cannot eliminate it.

Answer: No — a is redefined between the two occurrences, so a*b is not an available expression at the second point

Revision Sheet

EVERYTHING ON ONE SCREEN — LAST-MINUTE PASS
Compiler phases (order)

Lexical → Syntax → Semantic → IR generation → Optimization → Code generation. First four = front end (source-dependent). Code generation = back end (target-dependent). Optimization straddles both: machine-independent optimization (middle end) sits right after IR generation; machine-dependent optimization belongs with the back end.

Maximal munch

Lexer always matches the longest possible lexeme; ties between equal-length matches broken by rule priority order.

Left recursion → always non-LL(1)

A→Aα|β transforms to A→βA', A'→αA'|ε. Left-recursive or ambiguous grammars can never be LL(1).

FIRST vs FOLLOW

FIRST(α): terminals that can start a derivation from α (may include ε). FOLLOW(A): terminals that can appear right after A (never lists ε itself).

LR power hierarchy

LR(0) ⊂ SLR(1) ⊂ LALR(1) ⊂ CLR(1). LALR merges same-core CLR states — can create new reduce-reduce conflicts, never new shift-reduce ones.

Shift-reduce default

Conventional yacc/bison default resolves shift-reduce conflicts by shifting — correctly resolves dangling-else to bind with the nearest if.

Synthesized vs inherited

Synthesized: computed from children (bottom-up). Inherited: computed from parent/left-siblings (top-down/left-to-right). S-attributed ⊂ L-attributed.

3AC formats

Quadruples (op,arg1,arg2,result) — reorder-safe. Triples (op,arg1,arg2) reference by position — breaks under reordering.

Static vs stack allocation

Static = one fixed address, no recursion support. Stack = fresh AR per call, required for recursion. Heap = arbitrary lifetime, dynamic sizing.

Control link vs access link

Control (dynamic) link → caller's AR (actual call sequence). Access (static) link → lexically enclosing scope's AR (source structure). Coincide only when called from the direct lexical parent.

Static vs dynamic scoping

Static: resolved by source-code nesting, compile-time. Dynamic: resolved by the live call stack at runtime. Virtually all modern languages (incl. C) use static scoping.

Reaching definitions vs live variables

Reaching definitions: forward, union, def → later point. Live variables: backward, union, point → later use. Mirror-image data-flow problems.

Constant propagation

Replaces variables with known constants. Lattice: ⊤ → constant c → ⊥ (NAC). At join points: meet = intersection (c ∩ c = c, c₁ ∩ c₂ = ⊥). A variable is constant only if ALL paths agree.

Available expressions (for CSE)

Forward analysis, meet = intersection. OUT[B] = e_GEN[B] ∪ (IN[B] − e_KILL[B]). Expression a op b is available if computed on ALL paths and operands not redefined since.

Data-flow meet operators — the critical distinction

Reaching defs & liveness use union (∪) — any path suffices. Constant prop & available exprs use intersection (∩) — all paths must agree. GATE frequently tests this distinction.

Basic block leaders

Leader = first instruction, OR a jump/branch target, OR the instruction immediately after a jump/branch. Block = leader up to next leader.

Highest-value optimization target

Loops — since they execute far more often than straight-line code, loop-invariant code motion and induction-variable elimination give disproportionate speedup per instruction touched.

Practice — rapid-fire mix (original)

5 questions
Q1 A grammar is ambiguous. Can it be parsed by a CLR(1) parser?

No — ambiguity means some string has two distinct parse trees/derivations, which always manifests as a genuine conflict (typically reduce-reduce) in the parsing table of any deterministic LR-family parser, no matter how much lookahead is used. More lookahead resolves lookahead-limited weaknesses, not fundamental grammatical ambiguity.

Answer: No — ambiguous grammars cannot be parsed by any deterministic LR-family parser, including CLR(1)

Q2 Which phase would catch a type mismatch like adding an int to a struct?

Type compatibility isn't a question of token sequence (syntax) — the expression is grammatically well-formed. It requires knowing the declared types of the operands, which is exactly what semantic analysis checks using the symbol table.

Answer: Semantic analysis

Q3 True or false: a variable being "live" at a point guarantees it was also "reached" by some definition at that point.

False. Liveness asks "will the current value of x be used in the future before being overwritten?" while reaching definitions asks "which definitions of x may reach this point?" — these are independent analyses, and neither guarantees the other.

Counterexample: int x; if (cond) x = 10; printf("%d", x);. At the printf, x is live (its value will be used), but along the path where cond is false, no definition of x reaches that point — so a variable can be live without being reached by any definition.

Answer: False — liveness and reaching definitions are independent; a live variable need not have a reaching definition

Q4 Convert to postfix and generate 3AC for: x = (a+b)*c - d.

Following operator precedence (parentheses, then *, then -), break into elementary steps introducing one temp per operation.

Answer: t1 = a+b; t2 = t1*c; t3 = t2-d; x = t3

Q5 A function is called recursively 5 levels deep. What do the access links point to if the function is not lexically nested inside anything (a top-level function calling itself)?

Since the function is top-level (not nested inside any other function), it has NO lexically enclosing procedure at all — so the access link isn't pointing to some other function's activation record. What actually happens depends on the implementation: many textbook treatments model this by giving each activation record an access link to a shared global/static environment, but that "global AR" framing is a teaching simplification, not a universal rule — real implementations commonly resolve top-level/global names directly through the compiler's global/static data area (fixed addresses, a global symbol table, etc.) rather than through an access-link chain at all. Either way, the key fact holds regardless of implementation: since there's no lexically enclosing procedure, every one of the 5 activation records reaches the SAME global/static environment through whatever mechanism the implementation uses — this is unlike the control/dynamic links, which do chain caller→callee down the 5 levels.

Answer: All 5 activation records reach the same global/static environment (not each other's frames) since there's no lexically enclosing procedure — but exactly how that's implemented (a shared "global AR" vs direct static/global storage access) is implementation-dependent, not a fixed rule
